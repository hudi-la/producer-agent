# 基于信的判断，各用什么判据

> 开发文档。加一条判断之前先写进这张表，说清是**规则**还是**agent**。
> 最后核对：2026-08-19。

## 先分清三种「判断的人」

| 谁 | 是什么 | 判的东西会不会进产品 |
|---|---|---|
| **规则** | 纯函数 / SQL。不花钱，事实一变结果就变 | 会 |
| **Fairwind 内部 agent** | 产品跑起来之后自己调的模型（`brain/` 里那几条路） | **会**——判错了用户当场看得见 |
| **后台开发 agent** | 写代码时用来查库、核对、一次性清理的（比如我） | **不会**，产出的是迁移和文档 |

**这三者不许混。** 后台开发 agent 判过的东西必须落成规则或数据，
不能变成「因为当时那个 agent 看过所以是对的」——它下次不在场。

> 例：全库 3519 封信的草稿核对是后台开发 agent 做的，但结论**落成了
> `mail_label_audit` 表 + `classify` 里那两道闸**。以后再有草稿，
> 是规则挡掉的，不是靠谁记得。

## 一、规则判的（不花钱）

| 判断 | 判据 | 在哪 |
|---|---|---|
| 是不是一封真信 | Gmail 给了 `SENT`（我发的）/ 非 `DRAFT`（收的） | `brain/mail/addr.js` |
| 这封信属于哪条线 | `v_pa_pursuit_mail.on_this_line` 推导 | `0052`/`0053`/`0055` |
| 他回你了 | 最后一封进来的 > 最后一封出去的 | `cues.js` `repliedCue` |
| 该碰了 | 连发没回音几封 + 节奏 `[7, 21]`，满 2 次就停 | `cues.js` `bumpCue` |
| 说好的日子到了 | `next_touch_at ≤ 今天` **且那之后没来信** | `cues.js` `circlebackCue` |
| 还没回谢介绍人 | 有介绍人 + 对方回过你 + 没回谢过 | `cues.js` `thanksCue` |
| 见面 48 小时信 | 有见面记录 + 之后没发出过信 | `cues.js` `metCue` |
| 邮件类由头归线不归人 | `mail_on_line`（最后那封在不在线上） | `v_pa_cue_facts` |
| 卡面「新来信」 | 这条线上有对方来信晚于你上次看这张卡 | `v_pa_pursuits.new_mail` |
| 红点 | 最后一条是 Fairwind 说的、非 brief、晚于你上次看 | `v_pa_pursuits.unread` |
| 紧急 / 截止 | 14 天内或已过，**且还没交**（`stage` 不在 sent 之后） | `nextAction.js` `deadlineLine` |
| 上次碰 | 真信的最后一封（**重算，不是存的**） | `pa_recompute_touch` |
| 群发 | 信头里的 `List-Unsubscribe` / `no-reply` | `0045` |
| 这条线脏没脏 | 见第三节 | `v_pa_cue_facts.stale` |
| 引用块从哪开始 | Gmail `>` / `On…wrote:` / Outlook 下划线 / 签名线 | `src/lib/letter.js` |

**规则的好处**：你在邮箱里回了一封信，下次拉的时候由头自己就没了——
没有谁去执行「勾掉」，也就没有「该勾没勾上」这种 bug。

## 二、Fairwind 内部 agent 判的（花钱，判完存起来）

| 判断 | 判据 | 什么时候跑 | 存在哪 |
|---|---|---|---|
| **这封信要不要回** | 模型读信的内容 | 你打开通知栏 | `letter_verdicts` |
| **下一个该碰的日子 + 出处** | 模型读近期往来找时间锚点 | 你打开通知栏（重判） | `next_touch_at` + `next_touch_why` |
| **这个地址是不是真人** | 模型判 | 收信时，一地址一次 | `address_verdicts` |
| 建卡时讲懂这个机会 | 模型读网页 | 卡进来时 | `pursuit_messages` kind=brief |
| 起草回信 / 对话 | 模型 | 你说话时 | `pursuit_messages` |

### 三条硬规矩

**一、判不出来一律当「要回」。** 模型没答上、格式不对、网断了——
宁可多吵一条，绝不许因为一次调用失败把一封真信悄悄咽掉。
（`parseTriage` / `parseRejudge` 解析失败返回空数组，空数组 = 这批没判成。）

**二、日期和出处必须同时给，缺一个就都不写。**
两道闸：`parseRejudge` 里一道、`pa_set_next_touch` 里一道。
「你定的日子到了（8/17）」那句谎话之所以能出现，就是因为日期能单独存在——
而那个 8/17 其实是 Fairwind 自己写的（`next_action_by='fairwind'`）。

**三、判不成不推水位。** `pa_mark_judged` 只在真判完了才推进，
下次打开重判——**绝不假装判过了**。

### 什么不叫 agent

**框里那一两句摘要不叫模型。** 是截原文头一段（`saidThisTime`）。两条理由：

- 按信数花钱（几千封）违反「量锁在对象数上」（几十）那条规矩
- 更要紧：模型摘的那句**会跟原文分叉**，而原文就在一个「展开」的距离。
  截原文最坏是截得不好看，永远不会是假的。

### 花钱的量怎么锁住

| | 量级 |
|---|---|
| 重判 | 按**对象数**，只判最近 30 天有往来的，一批最多 12 个 |
| 判信要不要回 | 只判**球真在你手上**的那几封，一批最多 20 封 |
| 地址判定 | 一地址一次，判完永久有效 |

### 成本是按调用算的，不是按内容算的

实测（都是同一条路，只是带的内容不同）：

| 判几个 | 提示词多大 | 花了 |
|---|---|---|
| **1 个对象** | **773 token** | **$0.19** |
| 12 个对象 | 14,778 token | $0.235 |

**773 token 的活收 $0.19** —— 钱几乎全花在「发起这一次调用」本身上。
那 18k 是 agent SDK 自己的底座。试过三种压法，**一种都没压动**：

| 试了什么 | 结果 |
|---|---|
| 工具从 `['WebSearch','WebFetch']` 改成 `[]` | $0.19 → $0.20 |
| 换成只为判断写的最小 system（不带 Fairwind 人格、作品、履历） | 没变 |
| `maxTurns` 从 20 改 1 | $0.2016 |

判断这件事**确实不需要**知道作品、履历、协作弧、写信规矩 —— 那几样已经砍掉了
（`JUDGE_SYSTEM`，工具一个不给）。砍是对的，只是省不出钱：底座不是我传的。

### 所以唯一的杠杆是少发几次

| 参数 | 值 | 为什么 |
|---|---|---|
| 攒够几个就判 | **6** | 忙的时候快 |
| 最多攒多久 | **60 分钟** | 闲的时候兜底 |
| 一次最多带几个 | **30** | 反正跟带 1 个一样贵 |

60 分钟这个上限是拿「🔔 上那个数字能错多久」换的：新信进来 `needs_reply`
还没判、缺省当「要回」，数字可能虚高 1。一小时内可以忍，
而每次调用 $0.19 —— 一天判一次和判五次差五倍。

**稳态下一个窗口只有一次调用**：重判本来就会顺手判掉那封最后来信
（`rejudgeThese` 里调 `pa_judge_letter`），所以「单独判信」那条路
在稳态下是空的 —— 量过，0 封。

### 还有一条没走的路

底价来自 agent SDK 的底座，而 brain 走的是 Claude 订阅（没有 API key）。
如果接一个 API key 直接调 Messages API，773 token 的判断约 **$0.005**
—— 便宜 **40 倍**。代价是另一套计费。**这是要你拍板的事，没做。**

> 收窄之前：脏的 98 个全判，其中 72 个是半年以上没动的死线。
> 真跑过一批 12 个，**11 个结果是 null**——那种线上「约定了下一个时间点吗」
> 必然没有答案，模型加不进任何东西。收窄后 98 → 15。

## 三、什么算「这条线发生过事」（`stale` 的判据）

```
脏 = last_event_at > judged_upto
last_event_at = greatest(收信, 发信, 记一笔, 你在卡上做的动作)
```

**算的，不是存的。** 不用队列不用脏标记——队列会跟事实分叉，
这个项目吃过两次（`pa_seen` 在 localStorage 那次、过卡队列那次）。
水位漂了、判断中断了、迁移重跑了，下一次一算就知道。

### 算

| 事 | 从哪读 |
|---|---|
| 收到信 / 发出信 | 这条线上的信（`on_this_line`） |
| 记一笔 / 见面 / 决定 | `kind in (note, meet, decision)` |
| 移卡 | `pursuits.stage_at` |
| 改球权 | `pursuits.ball_at` |
| 勾掉 / 作废待办 | `next_action_done_at` / `void_at` |
| 打卡「聊过了」 | `contacts.last_touch_src='checkin'` |
| 回谢了介绍人 | `contacts.intro_thanked_at` |

### 不算（都是故意的）

| 事 | 为什么不算 |
|---|---|
| 你点开卡（`pursuit_seen`） | 看过不是新事实。算的话每张卡一打开就脏 |
| 通知栏按 ✓ / ✕（`cue_marks`） | 那是对由头的处置，不是新信息。算的话会「按了 ✓ → 变脏 → 重判 → 由头又冒出来」 |
| 改标题 / 备注 / 星级（`updated_at`） | 不改变「该不该动、什么时候动」。而且**重判自己会写 `next_touch_at`，用 `updated_at` 会自己把自己弄脏，无限循环** |

## 三·五、这些判据怎么测的

| 哪一半 | 怎么测 | 多少条 |
|---|---|---|
| JS（规则 + agent 的解析） | `npm test`（`node --test`） | 337 |
| SQL（视图、写口、派生值） | `select * from public.pa_selfcheck()` | 17 |

**两边都得跑。** JS 那半覆盖 `classify` 的四道闸、五种由头、
`deadlineLine` 的阶段判据、引用块怎么砍、`parseTriage`/`parseRejudge`
的解析和兜底；SQL 那半覆盖账本真假、`kind` 归类、三处读面的口径是否一致、
派生值有没有跟事实分叉、写口挡不挡得住坏数据。

加判据的时候**两边都要加一条**。SQL 那半没有测试框架，`pa_selfcheck()`
就是它的测试。

## 四、新信走哪几步

```
每 5 分钟一轮（brain 的 sweepMail + judgePass）
  ↓
① classify          四道闸，草稿和没发出的挡在这儿        规则
  ↓
② pa_add_mail       写成 kind='email'，落进往来表          规则
                    对话里当场看得见（v_pa_pursuit_thread）
  ↓
③ 这条线自动变脏     算出来的，不是标记                    规则
  ↓
④ 重判脏了的（每轮最多 12 个对象）                        Fairwind agent
     ├ 这段交流约定了下一个时间点吗 → 日期 + 出处，成对才写
     ├ 最后那封要不要回 → letter_verdicts
     └ 上次碰重算                                           规则
  ↓
⑤ 判还没判过「要不要回」的信（每轮最多 20 封）            Fairwind agent

你打开顶栏 🔔
  ↓
⑥ 只读。由头现算，拼成 手头 / 老账 / 判为不用回            规则
```

**①–⑤ 全在后台，你不用打开。** 这样 🔔 上那个数字在你看之前就是准的 ——
懒算的时候它不准：新信的 `needs_reply` 还没判、缺省当「要回」，
数字先 +1，等你打开才可能减回去。而你正是靠这个数字决定要不要打开。

### 重判之后影响到哪

| 重判写的 | 下游 |
|---|---|
| `next_touch_at` + `next_touch_why` | 通知栏的 `circleback` · 卡上「⏰ 该再碰一次」· 人卡「下次碰」格 · **下一次重判的上下文**（看得见现有约定，不会反复改） |
| `letter_verdicts`（`needs_reply` / `not_before`） | `repliedCue` 的两道闸 · 「被判为不用回的」那一层 · **🔔 的数字** |
| `contacts.last_touch_at`（重算） | 人卡「上次碰」· 通讯录排序 · `repliedCue` 的打卡闸 · 机构页 |
| `cue_judged.judged_upto` | 下一轮判不判（`stale`） |
