# 从 Fairwind 直接发信

2026-08-16

## 现在这条路是什么样

Fairwind 在中栏对话里写完一封回信，你**选中、复制、切到 Gmail、粘贴、改字、按发送**。

`cleanCopy.js` 存在的唯一理由就是这段路——从气泡里复制走的富文本会把纸色底
一起带进 Gmail，所以得在复制那一步把装饰扒掉。它是一个为"复制出去"服务的
补丁，而不是一个功能。

页面上那两颗「放进 Gmail 草稿箱」按钮（`Deliverables.jsx` / `PersonFocus.jsx`）
其实**够不着**：模型的工具白名单里没有任何一个能建产出（`server.js` 的
`READ_TOOLS` + 文件 + `GMAIL_TOOLS` 四件套），所以邮件从来没进过产出，
按钮下面永远没有东西可按。`PersonFocus.jsx` 那句「它写的草稿会出现在这儿」
是一句从未兑现过的话。

## 这次要改成什么样

信在产出里，你在产出里改，改完在产出里发。

### 那条护栏没有被拆，它被改写了

`brain/mail/auth.js` 顶上写着：

> scope 只有 gmail.readonly。**这个系统本来就发不出信**……不给写权限，
> 这条护栏就不是嘱咐，是结构上做不到。

这句话从今天起换成：

> **Fairwind 写得出信，但按不了发送键。**

具体做法：brain 的 scope 加一个 `gmail.send`（只发不读，最小增量），
但**发送是 brain 里一个纯 HTTP 函数，不在模型的工具白名单里**。模型够不到它，
跟它够不到别条线的文件是同一种"够不到"——结构上做不到，不是嘱咐。

不走 SMTP + 应用专用密码：那是一把长期明文凭证，而且 SMTP 没有 threadId，
发出去的信挂不回原来那串往来。

## 一封信的一生

### 一 · 对话里：信封

Fairwind 写完一封信，末尾多吐一个信封块，跟现有的 `[[FACTS]]` / `[[DRAFT]]`
一个路子：

```
[[LETTER]] {"to":"…","subject":"…","summary":"…","reply_to":"<msgid>","thread_id":"…"}
```

（不叫 `[[MAIL]]`：那个标记已经被同步那条路占了——`server.js` 里让模型
汇报「这次收到哪些新信」用的就是它。两处撞名，解析会互相咬。）

**这不是让它判断"该不该发"。** 它判断的只是"我这次写的是一封信"——
有收件人、有主题、有称呼和落款，这个它写的时候本来就知道，不用猜。

- `to`：收件人。从这条线的往来里挑最近那个对手方。
- `summary`：一句话，直接当 `pa_add_mail` 的 `p_content`（往来里那行摘要）。
  在这儿要，是因为它刚写完这封信，最清楚这封信在说什么——事后再花一次
  模型去总结自己写的东西是白花。
- `reply_to` / `thread_id`：如果是回某封信，带上原信的 `Message-ID` 和
  Gmail 的 `threadId`；新起一封就是 null。

信封只影响渲染和预填，**不触发任何写库**。解析失败（模型没吐、吐坏了）
就当没有信封——那条消息照旧是一段普通回复，你还能照老办法复制走。
信封坏了绝不能让整条回复不见。

### 二 · 你点「收进产出」

带信封的那条在对话里渲染成一张信卡，卡上一颗「收进产出」。

**点一下才进，不自动。** 形式判断归它（这是一封信），意图判断归你（这封要发）。
自动进的话，它把一段"示范一下语气"也标成信时，产出栏会长出你得去删的垃圾；
点一下的代价是每封信多一下，换来的是产出栏永远只有你认下的东西。

落成一份 `kind='email'` 的产出，`to` / `subject` / 正文一次填全。

**同一个所有者（一条机会线 / 一个人）名下只留一份待发信。** Fairwind 在对话里
改了五版，你收五次，覆盖的是同一份，不堆五份。理由跟 `0066`（重说）一样：
草稿的"最新一版"只有一个。

### 三 · 你在产出里改

用现成的 `pa_edit_deliverable`。收件人也是可改的一格，而且明摆在脸上——
**发错人是这个功能唯一无法挽回的失败**，所以收件人不许藏在折叠里。

### 四 · 发

「发送」按钮点第一下变成「确认发给 someone@example.com」，再点一下才真出去。
这一步只防一件事：发错人。

brain 的 `POST /mail/send`：

1. **身份校验**：`whoami()` 拿到已授权那个 Gmail 账号，跟 `profile` 里填的
   邮箱比对。不一致就拒发。发错人还能补一封道歉，**用错身份发出去的信
   连道歉都没处发**。
2. 组 RFC 822：`From` / `To` / `Subject`（非 ASCII 走 RFC 2047 编码）/ `Date` /
   `Message-ID`（自己生成，记下来）/ `In-Reply-To` / `References`。
3. **正文发 multipart/alternative（text/plain + text/html）**。
   库里的文字都是 markdown，`Md.jsx` 那条注释记着一次事故：同一份内容
   在两个地方渲染不同，粗体变成四个星号，「而且丑的那个看起来像坏了」。
   只发纯文本就是把那次事故复现到收件人的信箱里。brain 用跟前端**同一套**
   remark 栈（`remark-gfm` + `remark-breaks`）渲 HTML，保证屏幕上什么样、
   对方收到什么样。
4. `users.messages.send({ userId:'me', requestBody:{ raw, threadId } })`。
   带 `threadId` 才会挂回原来那串。

### 五 · 当场记账

Gmail 的 send 返回 `{ id, threadId }`，`id` 就是 `gmail_message_id`。

**顺序：先记账，后删产出。** 反过来的话，中间任何一步失败都会两头空——
信发出去了、产出没了、往来里也没有，那是这个系统能犯的最严重的错。

1. `pa_add_mail`：`p_role='artist'`、`p_gmail_message_id`=返回的 id、
   `p_counterpart`=收件人、`p_content`=信封里那句摘要（没有就退回正文首段）、
   `p_body_raw`=正文全文、`p_meta={subject,to}`。
2. `pa_mail_headers_upsert`：写一行 `direction='out'`，带上我们自己生成的
   `message_id` / `in_reply_to` / `refs`。
   **不能等下次同步再补**：0055 靠这几个头认亲，这中间对方要是回得快，
   那封回信就找不到自己的线。
3. 认领 thread：`pa_claim_contact_thread` / `pa_link_thread`。
4. 删掉那份产出（`pa_delete_deliverable`）。

**去重不用新写任何东西。** `pa_add_mail` 拿 `gmail_message_id` 做唯一约束，
下次全局同步从"已发送"里再收到这封时会 `on conflict do nothing` 撞掉。

### 球权不动

发信**不改球权**。0058 把球权改成了纯手动标签（`ball_eff` 直接等于你点的那个），
理由写在 `ball.js` 开头：系统算出来的判断会悄悄覆盖你的判断，而你收不到通知。
直发不是把那条规矩往回推的理由。

`Deliverables.jsx` 里那句「放进草稿箱不等于发出去，球权不会跟着翻」是 0058
之前的话，顺手改掉。

## 发失败了怎么办

产出**原样留着**，一个字不动，绝不写"已发送"。

- 授权掉了（改过 Google 密码、撤销过授权、scope 不够）→ 走现成的
  `MailAuthError`，界面上摆出那句 `fix`：在 brain 目录下跑 `npm run mail:auth`。
- **加了 `gmail.send` 之后必须重新授权一次**——旧 token 里没有这个 scope，
  不重授会报 403 insufficient permissions。这是升级时你要手动做的一步。
- 别的错（网络、Gmail 限流）→ 照 `gmail.js` 那套退避重试；重试完还不行就
  报到你脸上。

**一个不能省的护栏**：send 只重试**明确没发出去**的错（连接失败、4xx）。
一个超时的请求可能已经发出去了，盲目重试 = 同一封信发两遍。超时一律
不重试，报出来让你自己去 Gmail 已发送里看一眼。

## v1 不做

- **附件**。你现在发信前不加附件。要发带作品集的信时走那条白捡的退路：
  信进了产出，「放进 Gmail 草稿箱」那颗按钮**第一次变得可用**，
  放进去、去 Gmail 加附件、在那儿发。
- **批量发**。一次一封，你按一封。
- **抄送 / 密送**。
- **撤回窗口**。你选的是「我按，但在 Fairwind 里按」，不是「压几分钟再出去」。
  两段确认已经挡住了最常见的那一种错。

## 怎么验收

1. 在一条真线上跟 Fairwind 说「帮我回他」→ 对话里出现一张信卡（带收件人和主题）。
2. 点「收进产出」→ 右栏出现一份 `kind='email'` 的产出，收件人和主题已填好。
3. 让 Fairwind 再改一版 → 再收一次 → 产出还是**一份**，内容是新的。
4. 在产出里改几个字。
5. 按「发送」→ 变成「确认发给 xxx」→ 再按 → 信真的出去了。
6. 左栏往来里当场多一条「你」发的，「原文 ▾」能翻出全文；产出栏里那份没了。
7. 去 Gmail 看：信在**原来那串**里，不是另起一封；粗体是粗体，不是四个星号。
8. 跑一次全局同步 → 往来里**没有**多出重复的那一条。
9. 断开授权（或临时改坏 token）再发一次 → 产出原样留着，界面上是那句
   「跑一次 npm run mail:auth」，不是「已发送」。
