# 设计稿：看板七列 + 页面分区

> 日期：2026-08-04。状态：已实现（除文末「缓办」一节）。
> 上游：[2026-08-01 艺术家的 Producer Agent](2026-08-01-artist-producer-agent-design.md)

---

## 这一刀解决什么

界面到了「刚刚能用」的程度，但两处开始别扭：

1. **看板九列是照着「producer 在做什么」切的**，有几格之间并没有真正的停顿。
2. **顶栏一级放的是四个筛选**（其中三个还是死的），而真正该并列的三件事——追机会、维系关系、关于你自己——一个在首页、一个不存在、一个藏在右抽屉里。

这一刀重排这两处。视觉系统（字号/间距/颜色语义/CSS 组织）留到下一刀。

---

## 一、看板：九列并七列

### 列

| # | key | 列名 | 卡上文案 |
|---|---|---|---|
| 1 | `pending` | 新机会 | 读透了，等你批 |
| 2 | `matching` | 匹配项目 | 一起挑作品 |
| 3 | `writing` | 一起写 | 一起写中 |
| 4 | `sent` | 发出&提交 | 已交 |
| 5 | `replying` | 初次回信&继续沟通 | 沟通中 |
| 6 | `won` | 谈成 | 谈成 ✓ |
| 7 | `paused` | 暂停处理 | 暂停处理 |

### 为什么并

- **批准 + 挑作品 → 匹配项目**：你点头的那一下，接着就是挑作品。中间没有一次真正的停顿，它们是同一件事的两个瞬间。
- **不投 + 搁置 → 暂停处理**：都是这条线停下来了。**为什么**停下来是卡上的事，不是列的事。

### 为什么改 key 名

旧 key 按动作起（`brief` = 渡在读），新列名按状态起（新机会 = 等你点头）。两套词并存会让「看代码」和「看界面」对不上。

> 2026-08-04 补：第一列的显示名从「待批准」改成「**新机会**」。key 仍是 `pending`，行为不变。改名的由头是——它本来就是所有新卡的落点，「待批准」听起来像个审批环节，「新机会」才是它实际是的东西。已应用的 migrations（`0005`、`0015`）里的注释保留旧词，那是当时的记录，不回改。

**代价是真实的**：改这七个词动了 33 行数据、5 处代码、1 个数据库函数、1 个视图、2 个 scout prompt。这个代价正是文末「缓办」那节要根治的东西。

### 迁移（0015）

- `producer.stage_backup_0015` 先抄一份旧值——回滚一句 SQL 就够
- 默认值 `'proposed'` → `'pending'`（不改的话新卡会跳过你批准那一步）
- `pa_set_stage` 内部卡着旧九值白名单，换成新七值（**保持它原本的 `returns void` 形状**，只动白名单）
- [loadPursuits.js](../../src/lib/loadPursuits.js) 加了一层旧值翻译。**这层必须先于迁移落地**——否则前端已改、库还没迁的那段时间里看板会一列都筛不到，看着就像卡全丢了

> 血的教训：这次就是先改了前端才补翻译层，用户看到的是「卡片弄丢了」。对一个天天在用的系统，**看不见 = 丢了**。以后改数据形状，兼容层和改动必须同时落地。

### 验证

改前 33/76/59/4（机会线/消息/档案条目/联系人），改后一模一样，非法 stage 值 0 个。

## 二、行为不再挂在列名上

列以后要交给用户改名，所以要清点「哪些代码在认列名办事」。五条，留三撤二：

| 行为 | 处置 | 理由 |
|---|---|---|
| `pending` → 后台自动去读 | **留** | 「待批准」这个名字承诺的就是「已经读透了，等你点头」 |
| `paused` → 卡片变灰 | **留** | 收尾列，视觉上该退后 |
| `pending` → 新卡默认落这儿 | **留** | 得有个入口 |
| `writing` → 首页「今天需要你的」横幅 | **撤** | 今天该做什么不该由某一列决定 |
| 列 → 球在谁那边 | **撤** | 见下 |

留下的三条只挂在**内置列**上。用户以后自建的列不带任何行为，就是个纯粹的格子。

### 「讲懂」改成后台先读

原来是你点开卡才现读（`PursuitFocus` 里触发）。现在 [brain/server.js](../../brain/server.js) 每 60 秒扫一次「`pending` 里还没 brief 的卡」自己去读。`handleBrief` 本来就幂等，重复扫是安全的。

前端的 `requestBrief` 删了；sidecar 的 `POST /brief` 留着（手动补一张时用）。

### 球权不再从 stage 猜（0017）

0013 当初留了个兜底：没有外部往来时按卡在哪一列猜球在谁手里。**那是个错误**——「走到哪一格」和「现在该谁动」是两件事，用前者猜后者，猜出来的是一个看着很确定、其实没有依据的答案。

撤掉后只剩两个真实信号：

1. `next_touch_at` 到期或过期 → 该你动（外联唯一的引擎）
2. 最后一条真实对外通信（`kind='email'`）是谁发的 → org 发的该你回，artist 发的等对方

都没有 → `null`，卡上不显示球权那一行。**宁可不说，也不猜。**

代价看得见：待处理从 28 张掉到 1 张。那消失的 27 张本来就没有依据。手动钉住的球权不受影响。

## 三、页面分区：三个主区

一级导航从「四个筛选」换成「三个去处」：

| 主区 | 装什么 | 状态 |
|---|---|---|
| **项目争取** | 机会线看板 + 筛选 + 造卡任务 | 主战场 |
| **人际管理** | 没有 proposal 压力的关系 | 空页（诚实占位） |
| **我的档案** | 作品、履历、战绩、自述 | 原「战绩信息库」，抽屉 → 整页 |

这三个正好对上[上游设计稿](2026-08-01-artist-producer-agent-design.md)的「地基三样」：机会线、关系记忆、项目大脑。

### 分区判据：有没有 proposal 压力

- **有** → 项目争取
- **无** → 人际管理

**冷外联属于项目争取。** 它有明确图谋（我想去你那儿驻留），只是没有别人开好的申请表；它产出的仍然是一条机会线，走同一条弧。没有一张现存的卡需要搬去人际管理。

### 二级下沉

筛选（按阶段/截止/作品/来源）和造卡任务沉进项目争取自己的工具条。四个筛选**仍是占位**，没接上——怎么筛还在想，先留着位置。进到某条机会线时工具条收起（详情页是全屏的）。

### 我的档案为什么从抽屉升级成整页

抽屉默认「你只是来瞄一眼」。但这 59 条是渡判断匹配、写「为什么是我」、填申请字段的**全部弹药**。它够格当一级。

### 人际管理为什么值得单列

一度判断它「现在是空的、不该单列」——**这个判断是错的**。它空不是因为没有人，是因为那些人散在微信、WhatsApp、邮箱里，从来没进过系统。

而且它和机会线不是同一种东西，不是「按人看机会线」的镜头能盖出来的：

| | 项目争取 | 人际管理 |
|---|---|---|
| 基本单位 | 一条机会线 | 一个人 |
| 引擎 | 阶段 + 截止 | **多久没联系了** |
| 渠道 | 基本是邮件 | 微信 / WhatsApp / 邮箱，**每个人不一样** |
| 目的 | 交出去一份东西 | 说句话，讲点好玩的 |

现有 `producer.contacts`（name/email/org/role/notes）装不下多渠道和联系节奏。

将来大概是：一人一张卡（不挂在任何机会线上）· 记住用什么找他 · 「该联系了」提醒 · 上次聊到哪。造卡任务里的 **关系降温提醒**（`relationship_followup`）属于这里，已从项目争取的任务列表里移出。

**现在是空页，但不是白页**——页面上写清楚将来是什么、以及为什么现在空着。空页可以，骗人不行。

## 四、明确不改的

- **看板横向滚保持不变。** 7 列约 1600px 装不进一屏，这是当前想要的样子。
- **四个筛选 tab 留着占位。** 明知是死的，但位置要先占住。
- **视觉系统留到下一刀。** 字号/间距的魔法数、颜色语义（紫条/橙点/星星/球权各说各的）、`styles.css` 平铺 300 行——都不在这一刀里。
- **JSX 拆分不做。** 界面还会变，等稳定了再谈组件边界。

## 五、缓办：把列变成数据

> **不在这一刀里做。** 记在这儿，免得这些取舍只活在一次对话里。

### 为什么迟早要做

改七个列名动了 33 行数据 + 5 处代码 + 1 个函数 + 1 个视图 + 2 个 prompt。一个新用户想把「一起写」改叫「填表格」，按现在的做法得改代码、发版、跑迁移。**这条路走不通。**

根因：列是写死在代码里的，列名被抄在每张卡身上。

### 形状

新建一张表，一行 = 一列。卡不再存 stage 那个词，而是指向某一行：

```
producer.stages
  id · label（用户随便改）· sort（拖排序）· owner_id（谁的看板）
```

改名从此是 update 一行的 label——**不碰任何卡，不用迁移，不用发版**。

顺带：`pa_set_stage` 的白名单可以彻底删掉（外键天然保证合法，今天那个坑不会再有）；球权视图里写死的名单变成一次 join。

### 难点：行为怎么办

上面「留三条」的行为不能挂在用户可改的名字上。每一列除了名字还带几个标记：

| 标记 | 干什么 |
|---|---|
| `is_intake` | 新卡默认落哪列 |
| `auto_brief` | 进这列就后台去读 |
| `is_terminal` | 收尾列，卡片变灰 |

**名字归用户，行为归标记。** 用户改名不影响任何逻辑；加新列时选一个行为模板，或者不选——不带行为的纯格子也完全成立。

### 顺序

1. 把现在这七列搬进表里，key 和行为都不变，前端从表里读着画。单用户，先不加登录。
2. 界面上能改：改名、拖排序、加列、删列。**删非空列必须指定卡搬到哪去**，否则就是丢信息。
3. 多用户：`owner_id` + RLS + 新用户开号时灌一套默认列。这一步才需要登录系统。

第 1 步应排在「视觉系统」之前——它会改动 Pipeline 的数据来源，顺序反了要返工。
