# 判断得有执行点

> 日期：2026-08-19。状态：**设计稿**。
> 上游：[8/18 顶栏通知](2026-08-18-notifications-design.md)
> 起因：通知栏第一次真用，八条全错。三个根因修完两个（`0075`–`0077`），
> 剩下这一个是结构性的。

---

## 一、病：没有任何时刻会发生「重判」

通知栏报的「你定的日子到了（8/17）」是编的；Sarah 那条你早就 follow up 过、
对方还回了「plan on 2027」，它还在报老账；Stanford 你已经移到「发出&提交」，
它还在喊截止。

三件事的共同点：**系统拿着一个陈旧的结论在说话，而没有任何时刻会去更新它。**

写 `next_touch_at` 的是 [`handleRefresh`](../../brain/server.js)，而它是死代码：

- `refreshPursuit` 在 `App.jsx` 里只 import 没调用（`runRefresh` 随 8/06 那一刀走了）
- 全局收信走 `/mail/sync` → `incremental()`，**纯收信，不消化**

所以库里那几个 `next_touch_at` 是历史遗留，不是活的。我在 `0072` 又加了一列
`next_touch_why`，**同样没有任何东西写它**——跟 8/12 稿子骂 `next_action`
的话一字不差：「留着就是一行永远不会更新的字，比空着更坏」。

## 二、判断的输入不只是邮件

> 移卡这件事情本身也是包括判断的。

对。你把 Stanford 移到「发出&提交」，**那就是你说了「这件事我做完了」**。
系统有这个事实，却不看它。

会改变判断的事有四种，现在一种都不触发重判：

| 发生什么 | 现在 | 该 |
|---|---|---|
| 收到信 | ❌ | ✓ |
| 发出信 | ❌ | ✓ |
| **你移卡** | ❌ | ✓ |
| 你记一笔 / 打卡 | ❌ | ✓ |

## 三、新规矩：脏了就重判，脏不脏是算出来的

**不用队列，不用脏标记。** 队列会跟事实分叉——这是这个项目反复吃过的亏。

每个对象记一个水位 `judged_upto`：上次重判时，看到的最后一件事发生在什么时候。

```
脏 = 这个对象最后一件事的时间 > judged_upto
```

`最后一件事` = max(最后一封信, 最后一笔/见面记录, **移卡的时间**)

三样都是库里查得到的事实，所以「脏不脏」是**算出来的**，不是存的。
水位漂了、判断中断了、迁移重跑了——下一次一算就知道，不会有「明明脏了
但标记丢了」这种状态。

### 移卡要留下时间戳

`pursuits` 上没有任何一列记「阶段是什么时候变的」。`updated_at` 不能用：
它任何一次 update 都会动，而重判本身就会写 `next_touch_at`——**那会把自己
变成脏的，无限循环**。

所以加一列 `stage_at`，只由 `pa_set_stage` 写。

## 四、重判产出什么

读这个对象**近期的往来**（含你发的、他回的、你记的一笔），答三样：

| 产出 | 落到哪 | 规矩 |
|---|---|---|
| 下一个时间点 | `next_touch_at` + `next_touch_why` | **两个必须同时给，缺一个就都不写** |
| 这封信要不要回 | `letter_verdicts`（沿用 `0073`） | 判不出来当「要回」 |
| 水位 | `cue_judged.judged_upto` | 只有真判完了才推进 |

第一条是你要的那件事：

> Sarah 已经回复了，告诉我说会把课排到明年。那么你应该根据这个交流设定一个新的
> follow-up 时间。

她原话是「I think we should plan on 2027」——重判读到这句，写
`next_touch_at = 2027-01-05`、`next_touch_why = '她说 "plan on 2027"'`。
到那天，这条会带着出处响一次。

**日期和出处同一次写入产生，谁也不许单独存在。** 这是第一条病的直接对策：
`pa_set_next_touch` 两个参数缺一个就拒绝写，从库这一层堵死。

## 五、什么时候跑：变脏就判

> **这一节改过一次。** 第一版是懒算——「打开通知栏时判一批，不看就不花钱」。
> 那个理由错了两处，都是被一句「为什么要打开通知栏才开始重判」问出来的。

### 错在哪

**一、成本算错了。** 「不看就不花钱」是拿 **98 个积压**估的。可那 98 个是
一次性的历史包袱（水位表刚建，全库都算脏）。数了一下稳态：

| 日 | 那天变脏的对象数 |
|---|---|
| 8/19 | 4 |　| 8/18 | 5 |　| 8/17 | 6 |
| 8/16 | 8 |　| 8/15 | 1 |　| 8/14 | 3 |

**一天 1–8 个**，一批 12 个约 $0.2 —— 攒成一批的话一天不到两毛钱。

> **但这里我又算错了一次，改完真跑才看见：成本是按调用算的，不是按对象算的。**
> 每次调用带两万 token 的上下文 —— 实测判 1 个 $0.19、判 12 个 $0.235。
> 所以「变脏就立刻判」会变成一天 5 次调用 ≈ $0.95/天。**得攒够了再判。**

**二、更要紧：🔔 上那个数字是在重判之前算的。**

一封新信进来 → 对象变脏 → 但 `needs_reply` 还没判，**缺省当「要回」**
→ 数字 +1。那封信要是「谢谢，回头见」，这个 +1 就是假的 ——
**而你正是靠这个数字决定要不要打开**。

懒算等于说：你得先打开，它才肯把数字算准。可数字的用处就是让你决定开不开。
这跟这一整刀在治的病是同一个：**系统拿着还没更新的结论说话。**

### 现在怎么跑

挂在收信循环上（`sweepMail` 之后），**每轮都跑，有活就干**：

```
每 5 分钟
  ├ 收新信
  └ judgePass()
      ├ 重判脏了的      一批最多 30 个对象
      └ 判还没判过的信   一批最多 20 封
```

那两个上限是防止单次调用太大，**不是为了省钱**。

> 中间试过一版「攒够 6 个或 60 分钟才判」，为的是少发几次省订阅额度
> （每次调用有个跟内容无关的底价，约 18k token，是 agent SDK 自带的）。
> **撤掉了**：这条路本来就是临时的，而额度够用 ——
> 省额度是拿「🔔 上那个数字能错多久」换的，不该拿它换。

**稳态下一个窗口只有一次调用**：重判本来就会顺手判掉那封最后来信
（`rejudgeThese` 里调 `pa_judge_letter`），所以「单独判信」那条路
在稳态下是空的 —— 量过，0 封。

## 六、顺带修：「紧急」也不看阶段

Stanford 在通知栏喊截止，在「紧急」筛选里也在。病根同一个：
[`deadlineLine`](../../src/lib/nextAction.js) 从第一行到最后一行只看日期，
一个字没提阶段。

截止的意思是「什么时候之前得交」，**交了之后它就不再是待办**。
已经到「发出&提交」及之后的阶段，不再算紧急。

（`deadline` 那条由头 `0077` 已经整个撤掉了，这儿修的是卡面和筛选。）

## 七、这一刀不做的

- **不重做 `next_action` 的显示**。重判只写 `next_touch_at/why`，
  `next_action` 继续只当出处读。
- **不在收信时同步判**。
- **不动卡面四个信号、红点、过卡队列。**

## 八、验收

1. 把一张卡移到「发出&提交」→ 那条线当场算脏 → 下次打开通知栏会重判
2. Sarah 那条重判之后，`next_touch_at` 落在 2027 年初，`why` 里带得出
   「plan on 2027」这句原话
3. 只给日期不给出处 → `pa_set_next_touch` 拒绝，两个都不写
4. 重判自己写 `next_touch_at` **不会**把自己变回脏（`stage_at` 不动，
   `updated_at` 不参与判据）
5. 通知栏第一次打开会报「还有 N 个要判」，判完再打开是 0
6. Stanford 已经在「发出&提交」→ 卡面不写「截止 · 今天」，「紧急」筛选也筛不到它
