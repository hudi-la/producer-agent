# 一个库,很多艺术家 —— 多租户与隔离

2026-08-24

## 为什么是这个形状

workshop 要把这套系统交给学员用,而学员里**没有一个人有工程能力**。所以
「用户自己拥有、自己维护」不成立:vibecoding 写出来的多余数据往返、状态机
规则打架,这些坑他们修不了,只能由作者修一次、推给所有人。

而「每人一个库、作者持有全部」在钱上是坏的:10 人约 $115/月、30 人约 $325/月,
**随人数线性涨**,对着一次性 $300 的学费。唯一成立的形状是**不随人数涨**的:
一个库,很多人,约 $35/月封顶。

代价是隔离从「不同的数据库」变成「写对的权限规则」。所以这一刀的重点不是
搬数据,是**证明隔离**。

## 今天是什么样

- `producer.profile` 上有 `unique(singleton)`：**结构上只准有一个人**
- 三十多张表**没有一张有归属列**
- `producer` schema 上**一条行级权限规则都没有**
- 八十六个 `pa_*` 函数全是 `security definer` + `grant to anon`：
  **拿到匿名钥匙就能读写整个库**
- 没有登录这回事
- brain 在学员本机跑，手里是 `SUPABASE_SERVICE_ROLE_KEY`（绕过一切检查）

唯一的伏笔：`pursuit_seen` 带了 `profile_id`（0030 的注释写着「为了以后真有
第二个人」）。

而且 **0001 的最后一行早就写好了这一刀**：
> `NOTE: RLS is intentionally deferred for the self-use first slice.`
> `Before this is multi-user, enable RLS on producer.* and scope by an artist_id.`

### 实测清单（2026-08-24 从生产库读的）

`producer` schema 共 **25 张表**，**开了行级权限的：0 张**。带归属列的只有 2 张：

| 已有归属列 | 要加归属列（23 张） |
|---|---|
| `cue_marks`、`pursuit_seen`（都是 `profile_id`） | `address_verdicts` `attachments` `contact_emails` `contact_orgs` `contacts` `cue_judged` `deliverables` `letter_verdicts` `mail_accounts` `mail_headers` `mail_label_audit` `message_tags` `org_mailboxes` `profile` `pulse` `pulse_areas` `pursuit_messages` `pursuit_parties` `pursuit_threads` `pursuits` `tasks` `works`（`stage_backup_0015` 是备份表，随 0015 一起清理） |

回填零风险：今天库里只有一个人，所有现存行都归他。

## brain 往哪放：留在本机，但换身份

多租户之下，万能钥匙**不能**待在学员的笔记本里——十台机器上的十把万能钥匙，
等于十个人都能读所有人的信。

两条路，选第二条：

| | 搬到作者的服务器 | **留在本机，用学员身份连库** |
|---|---|---|
| 数据库成本 | 不涨 | 不涨（$35/月封顶）|
| 算力成本 | **随人数涨**——刚否掉的形状从后门回来 | 各付各的，在各自机器上 |
| API key | 作者替所有人保管 | 学员自己的，本地 |
| Gmail 授权 | 作者保管 | 本地 |
| 万能钥匙 | 只在服务器上 | **谁都没有** |

选第二条还顺手拆了今天最吓人的那颗雷：`brain/README.md` 警告过的
「agent 可能同时拿到 Bash 和 service_role」——以后本机上根本没有万能钥匙。

**代价**：brain 要改成用学员的登录令牌连库，于是行级权限规则**对 brain 也生效**。
这是对的：边车不该是特权进程。

## 做什么

1. **登录**：用 Supabase Auth 现成的，不手写。
2. **归属列**：三十多张表加 `owner`。**回填零风险**——今天只有一个人，
   所有现存数据都归他。
3. **行级权限规则**：每张表都要，不留白。
4. **九十七个函数**：逐个按「当前登录的是谁」过滤。`security definer` 保留，
   但函数内部认 `auth.uid()`，不再无条件信任调用者。
5. **brain 换身份**：不再用 `SUPABASE_SERVICE_ROLE_KEY`，改用学员的会话令牌。
6. **前端**：登录页 + 会话。
7. **`profile` 拆单例**：去掉 `unique(singleton)`，一人一行。
8. **种子/演示数据的护栏重想**：`demo_guard` 现在查的是「那唯一一行 profile
   的 is_demo」，多人之后这个判据不成立。

## Gmail 通路统一到自己的 OAuth

今天有**两条**：brain 自己的 OAuth（`npm run mail:auth`，收信 + 发信），和
claude.ai Gmail 连接器提供的四个工具（`search_threads` / `get_thread` /
`get_message` / `create_draft`）。第二条绑在 claude.ai 账号上，**API key 那条路
上根本不存在**——所以统一不是清理，是第一项的前提。

成本比看上去小：**四个工具里三个是读，现有的 `gmail.readonly` 已经覆盖**。
只有 `create_draft` 要新加一格 `gmail.compose`。加 scope 之后必须重跑一次授权，
症状（403，长得不像缺权限）`brain/README.md` 已经写过。

**时机（2026-08-24 定）**：这一段**暂缓**。它动的是他每天在跑的收发链路，
而他正在个人版上调发信功能（「我自己用着都不好用」）。等发信调稳再做，
避免两条线改同一片代码。存草稿的许可（`gmail.compose`）和接口位置留着，
发信相关功能在 workshop 版上暂不开发。

### ⚠️ 统一会拿掉一个靠「别人没做」撑着的护栏

`server.js` 的注释写着：claude.ai 连接器**整套工具里没有 send**，所以
「Fairwind 发不出去信」不是我们关的，是那个能力不存在。

改用自己的 OAuth + `gmail.compose` 之后，**令牌本身具备发信能力**。agent 能不能
发，从此只取决于我们给不给它这个工具。

这是那条文案红线（「最终的字是你的、你来发送」）的技术底座。今天它结构性成立，
统一之后它必须**刻意重建，并且用测试钉住**：断言给 agent 的工具清单里没有任何
发信能力。一次看着像纯清理的重构，会悄悄把它拿掉。

## 授权和前端都留在本地

**Gmail 授权搬到页面上**：brain 本来就是本地 HTTP 服务、页面本来就在跟它说话。
加一个端点起 OAuth 流程，页面上一个按钮 + 「已连接 / 未连接」状态。比让学员
在终端里跑命令、再自己判断成没成功强得多。

**前端也跑在本地**，跟 brain 同一个包、一条命令一起起来。托管的只有数据库。

理由：如果前端是托管的 https 页面，学员的浏览器要访问本机的 brain
（`http://localhost:8788`）。Chrome 通常放行（localhost 有特殊待遇），
Safari / Firefox 不一定。这类失败**学员一个都修不了**，而且症状是「页面一直转圈」
这种毫无线索的样子。前端留本地，整类浏览器差异问题不存在。

成本不变（数据库仍是唯一托管的东西，$35/月封顶），更新仍然中心化（拉最新版）。

## 判据：隔离必须是机器证明的，不是小心出来的

**权限规则出错是静默的**——不报错，只是多返回了几行。人工检查看不出来。

所以这一刀的验收不是「写完了」，是一套**隔离测试**：

- 建两个测试用户 A / B，各自写一份完整的数据（机会线、往来、联系人、作品、盒子）
- 对**每一张表**断言：以 A 的身份查，B 的行数为 0
- 对**每一个 `pa_*` 函数**断言：A 传 B 的 id 进去，拿不到东西、也改不动
- 对 **brain 的每个端点**断言同一件事

这跟 `prompt.test.js` 里那把「一个字都没丢」的尺子是同一个思路：把一条**性质**
钉成会变红的测试。「数据不会泄露」是对艺术家的承诺，内容是他们跟策展人、
基金会的私人通信——这条承诺必须由测试守着，不能由记性守着。

## 顺带变便宜的和变贵的

**变便宜（但没有消失）**：数据库那半边的安装没有了——学员不建库、不跑迁移、
不碰后台。**但 brain 还是得装在每个人的机器上**，所以「一键安装」仍然是
9/15 之前的必做项，只是范围缩小成 brain 这半边。

而且 brain 这半边**多了一步**：它现在要用学员的身份登录，不再是填一把万能钥匙。

剩下的安装里最难的是 Gmail 授权。解法是**作者建一个 OAuth 应用，学员共用**：
Desktop 类型的 client secret 本来就不算真秘密，可以随 brain 一起发。于是
`brain/README.md` 现在那五步（建 GCP 项目 / 启用 Gmail API / 在 Audience 页
PUBLISH APP / 建 Desktop client / 填两个密钥）**对学员整个消失**，只剩
「跑一次 `npm run mail:auth`，在警告页点继续」。

README 里已经证实：未验证也能 publish，只是授权时多一个警告页，而 published
的 refresh token 是长期的（Testing 状态下 7 天就过期，那会以「这轮 0 封新信」
的样子静默挂掉）。未验证应用有用户数上限，十人量级用不到——跟多租户那件事
同一个形状：现在够用，几百人时再说。

**学员那端最后剩下的**：装 Node 和这个包 → 跑一次 setup（登录、填自己的
模型 API key）→ `npm run mail:auth` 点一下 → 把 brain 跑起来。

**装机的时间点（2026-08-24 定）**：课前完成，开课前约**装机答疑**；
第一节课不当装机大会。

**多租户的落地库（2026-08-24 定）**：在一个**新的 Supabase dev 项目**上做，
顺便把 106 支迁移从零重放一遍、清掉 0111–0114 的重号——这本来就是
「一台干净机器从零验证」的一部分。**他的生产库在合并之前一支新迁移都不吃。**

**变贵（但比想的少）**：所有学员的流量走作者这一个项目，egress 从此是作者的
账单。查过了：**Pro 含 250 GB/月，超出 $0.09/GB**；MAU 含 10 万；每项目含
8 GB 磁盘。按现在的单人用量，十人到三十人都碰不到这些线。

所以**成本是 $35/月封顶，而且一直封到远超三十人**——这正是选它的理由。
`docs/specs/2026-08-21-egress-diet.md` 那轮省流量的活儿仍然值得（它省的是
响应速度和上下文钱），但它不再是账单上的风险。

## 不做

- **brain 搬上服务器**。见上表：算力成本会随人数涨，正是被否掉的形状。
- **付费托管别人的 API key**。同上，而且是另一层责任。

## 时间

这件事和「模型分层 + API key 通路」「scout 抽离」并列在 9/15 之前。
它替换掉了原来的「一键安装」，不是外加。

语气搬进库（见 `2026-08-24-the-voice-is-data.md`）仍然可以拖到第三节课之前，
但它要**跟着归属列一起设计**——那张表天生就该是每人一行。
