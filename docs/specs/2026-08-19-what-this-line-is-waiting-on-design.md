## 〇、第一稿错在哪

第一稿把所有情形压成一个通用的「每封信问四件事」。而正确的做法是：
**问什么取决于当时的 state 和来的 event** ——

- 等对方回的时候来了对方的信，问的是「它解决了等的那件事吗」；
- 你发出一封信，问的是「它在等对方做什么、按惯例等几天」；
- 你欠着回信的时候你发出了信，问的是「这封回了那件事吗」。

第一稿还有一处直接违反规则：SQL 里对方**任何**回信都会关掉「等对方回」——
「收到，回头看」这种客套话也关。第二稿里关闭只能由**判断**（标签）触发，
见第九节。

## 三、清洗和归属（第一稿这部分没错，保留）

**清洗**——是不是一封「有信息的信」，两层判据：

- 信头和标签（不花钱）：`DRAFT` / 你发的但没 `SENT` / bulk / no-reply /
  主题以 `Accepted:` `Declined:` `Tentative:` `Canceled:` `Invitation:` 开头
- 内容（模型）：真人写的但没有实质内容的（纯客套、自动确认）

**归属**——这封信是谁的、哪条线的：

```
是现有的人 / 现有的机会线吗？
├ 是 ──▶ 收进那张卡：对话、往来、上下文，一个模块都不落
└ 否 ──▶ 该不该建新联系人？该不该挂到某条线？（判据含信的内容，不只发信人）
         ├ 该 ──▶ 建 / 挂，然后同上
         └ 都不该 ──▶ 通知栏出一条：
             「邮箱收到一封邮件/发出一封新邮件，「内容梗概」，
               无法归到任何线中，可到后台处理。」 【不再提醒】
```

**【不再提醒】只关这一条提醒，不删信。** 信永远留在账本里。

## 四、转移表

每张表四列：**来了什么 → 问 Fairwind 的那句话（原话）→ 转到哪 → 你看见什么**。
「规则」标注的格子不花钱，纯代码判。

### `IDLE`

| Event | 问什么 | 转到 | 你看见什么 |
|---|---|---|---|
| `THEIR_LETTER` | 「这封信：① 要你回吗？凭什么？② 约了日子吗——见面，或对方说某天联系你？③ 都不是？」 | ①→`NEEDS_REPLY`；②见面→`MEETING_SET`，某天联系→`WAITING_REPLY`(due=那天)；③→`IDLE` | 按转入的 state 显示（见各自的表） |
| `MY_LETTER` | 「这封信在等对方做什么吗？等什么？**按这类事的惯例该等几天**——投申请、约时间、问一句，各不一样。还是纯告知/收尾致谢，不等什么？」 | 等→`WAITING_REPLY`；不等→`IDLE` | 等→等待栏出现一条 |
| `NOTE` | 「这笔说了什么：见了面？办完了某件事？约了日子？」 | 见了面→走 `DEBRIEF` 的产出链；约了日子→`MEETING_SET`；其他→`IDLE` | |

### `WAITING_REPLY`（在等：X，due D）

| Event | 问什么 | 转到 | 你看见什么 |
|---|---|---|---|
| `THEIR_LETTER` | 「我们在等：**X**。这封信解决了它吗？(a) 解决了 (b) 只是客套/说收到了，没解决 (c) 说的是别的事」 | (a)→关掉，这封新信按 `IDLE`×`THEIR_LETTER` 重判；(b)(c)→**due 不动** | (a) 等待栏那条消失，按新判的结果出新的 |
| `MY_LETTER` | 「这封有没有把等的事**换掉或作废**？」（例：你主动写「那件事算了，另问一句…」） | 换了→更新 X；没换→**纹丝不动，due 不重置**——你连发三封不能变成永远等不到点 | |
| `NOTE` | 「这笔解决了 X 吗？」（「电话里说定了」「表单已提交」【已处理】） | 解决→关掉，重判下一步；否则不动 | |
| `TIMER`（到 D） | **这一刻才起草** follow-up。起草的同时问：「这封 follow-up 发出后，该等对方什么、等几天？」 | 挪进「该动的」；你把草稿发出去时走 `MY_LETTER` 那行，进入新的 `WAITING_REPLY` | 「「某某人/机构的某某事务」，已经过去 N 天，follow up 已经起草【打开卡片】」；草稿出现在卡的对话里 |

没到 D 时，等待栏显示：
「「某某人/机构的某某事务」，已经过去 N 天，设定 follow up 时间为 X 月 X 日。」

### `NEEDS_REPLY`

进入这个 state 的**当下**就判一次（规则+模型）：「Fairwind 手上的信息够起草吗？」
够→直接起草，发进卡的对话；不够→在卡里问你→`INFO_NEEDED`。

| Event | 问什么 | 转到 | 你看见什么 |
|---|---|---|---|
| `MY_LETTER` | 「这封回了那件事吗？」 | 回了→关掉，这封信再按 `IDLE`×`MY_LETTER` 判它自己等不等对方；没回→不动 | 回了→「该动的」那条**自动消失**——你做好的事自动取出来，不再显示 |
| `NOTE` /【已处理】 | 规则：一条 NOTE 就关 | 关掉 | 真例：**Weidi**——你在微信上加了他，系统看不见邮箱外的事。按一下【已处理】= 记一笔「微信上加了」，这条就关了。这正是这个按钮存在的理由 |
| `THEIR_LETTER` | 「对方又来一封：现在要回的整体是什么？」 | 仍是 `NEEDS_REPLY`，「主要内容」更新成合并后的 | 通知上那句梗概更新 |

显示：「「某某人/机构」发来邮件，「主要内容」需要回复【打开卡片】」——
「主要内容」旁边**要显示判『要回』的理由**（现在完全不显示，这是欠账）。

### `INFO_NEEDED`

| Event | 问什么 | 转到 | 你看见什么 |
|---|---|---|---|
| `YOUR_ANSWER` | 拿你的回答起草 | 回到 `NEEDS_REPLY`（草稿好了，等你发） | 草稿出现在卡的对话里 |
| `THEIR_LETTER` | 重判——对方可能自己把缺的信息补上了 | 视答案 | |

### `MEETING_SET`（约在 M）

| Event | 问什么 | 转到 | 你看见什么 |
|---|---|---|---|
| `TIMER`（M 日早） | 规则 | 不变 | 「该动的」：「「某某人/机构的某某事务」，记得今天见面【打开卡片】」 |
| `TIMER`（M 结束） | 规则；Fairwind 在卡里问你见得怎么样 | `DEBRIEF` | 通知换成：「今天见面怎么样？【打开卡片】」 |
| `THEIR_LETTER` | 「日子变了吗？取消了吗？」 | 改期→更新 M；取消→按 `IDLE` 重判 | 等待栏那条的日期跟着变 |

> **数据源是新的**：M 得从信里读出来存。现在哪儿都没记——Biayna 那句
> 「9/11, 12pm, 我发链接」在 Fairwind 自己参与讨论的卡里，库里却查无此约。
> 电话里约的靠你记一笔；接日历是以后的事。

### `DEBRIEF`

| Event | 问什么 | 转到 | 你看见什么 |
|---|---|---|---|
| `YOUR_ANSWER`（见成了） | 你的回答本身存成一条 kind='meet' 的笔。然后判两条：①「这次见面是单人私谊，还是多人/明确是某条线的对公会面？」②「对方有介绍人吗？这算介绍后第一次真联系上吗？」 | ①单人→那个人挂 `OWE_MEETING_NOTE`；多人或对公→挂那条线；②是→**介绍人**挂 `OWE_THANKS` | 人际管理页出现对应条目 |
| `YOUR_ANSWER`（没见成） | 「下一步：改约？等对方？不了了之？」 | `MEETING_SET` / `WAITING_REPLY` / `IDLE` | |

### `OWE_THANKS`（挂在**介绍人**身上）

**触发**：被介绍的人**回了你的信或见了面**——只发出去没人回不算联系上。

| Event | 问什么 | 转到 | 你看见什么 |
|---|---|---|---|
| （进入时） | 起草谢信，发进**介绍人**的联系人卡 | | 人际管理页「该动的」：「见到了「某某」介绍的「某某」，跟他说一声谢谢。」 |
| `MY_LETTER`（给介绍人） | 「这封谢过了吗？」 | 谢过→关 | 那条消失 |
| `NOTE` /【已处理】 | 规则：关 | 关 | |

真例：**Weidi 介绍了 Ana 和 Biayna，两条都联系上了** → Weidi 头上是一条
`OWE_THANKS`，带两个理由 → **一封谢信提两个人**，不是两封（见第六节合并）。

### `OWE_MEETING_NOTE`

| Event | 问什么 | 转到 | 你看见什么 |
|---|---|---|---|
| （进入时） | 起草那封 48 小时信，发进对应的卡（单人→人卡；多人/对公→线卡） | | 人际管理页「该动的」：「和「某某」meeting 了，回复一下。」 |
| `MY_LETTER` / `NOTE` | 「这封/这笔了了这件事吗？」 | 了了→关 | 那条消失 |

## 五、TIMER 到点起草——就这一刻，不提前

**判断出来不起草，到点才起草。** 等 5 天的那封，第 5 天才动笔——
中间对方回了，那次调用就省了。等几天由**起草那次调用**顺手定
（`IDLE`×`MY_LETTER` 那格的问题），5 / 14 天只是它拿不准时的兜底。

范围：

| | 自动起草 |
|---|---|
| 现有机会线的卡归进了新信 | **是** |
| 人这边（谢信、48 小时信） | 只对 **2026-08-03**（Fairwind 开工）之后建的线 |
| 归不到任何地方的信 | 否——只出第三节那条提醒 |

## 六、合并

同一个人身上同时挂着两件事（例：线卡上 `NEEDS_REPLY` + 人卡上
`OWE_MEETING_NOTE`）→ 问 Fairwind：

> 「按惯例，这件事是**等 follow-up 的时间一起发**，还是**可以先发一封**？」

合并进**后发生 event** 的那张卡；两个列表加起来**只出现一次**；
Fairwind 的对话以后事件的卡为中心；早的那张卡留一句简短说明。

真例：Weidi 的两条介绍（Ana、Biayna）→ 一封谢信提两个人。

## 七、两栏分工

> **机会线的事进通知栏，人的事进人际管理页的「该动的」栏。**

判据是**挂在哪张卡上**，不是长什么样：只挂在联系人身上、放不进任何线的，
**即便是 `NEEDS_REPLY` 也进人际管理页**。

每栏两个区：

```
该动的  （3）      ← 到点了的（due）
等待    （12）  ▸  ← 没到点的，折叠，数字一直露在外面
```

**🔔 上的数字数全部**（该动的＋等待＋老账＋判为不用回），不只数「该动的」。

> 这一节撤回 8/19 早些时候删掉人际管理页「该动的」那一刀。这次不同：
> 两栏装的是**不同的事**，合并规则保证一件事只出现一次。

## 八、卡面上那行金色字

当前 state 的那句话（在等什么 / 该做什么 + due）显示在卡的**封面**上，
跟截止时间一样是金色的：

```
CultureHub Resident Artist · 2026–27
★★★
等 Mattie 九月初把 Joo 介绍给你 · 9/1        ← 金色
```

跟球权那两个按钮**并排，不互相覆盖**：球权是你随手记的便签，系统不读它；
这行金色字是系统算出来的。两个不一致，就让你看见不一致。

## 九、存什么、算什么

> **每次判断都存**——锚在引发它的那条事实上（一封信、一条笔、一次回答），
> 记下问的是哪一格的问题、答了什么、凭什么。
> **state 不落表**——把这个对象的事实和标签按时间重放，算出来。

`letter_verdicts` 从没分叉过，因为它锚在一封信上——信的内容永远不变，
判一次永远算数。这套标签是同一个思路，只是锚点扩成 `pursuit_messages.id`
（那张表里信、笔、见面、决定本来就并排放着，一套锚点全盖住）。

**关闭 `WAITING_REPLY` 的唯一途径是标签**（那封信被判为「解决了」），
不是「存在一封对方回信」这个事实本身——这就是「收到，回头看」不误关的机制位置。
