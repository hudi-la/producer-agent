## 一、三条病

### 一、Fairwind 说的「到时候再 follow up」是说过就算的一句话

它有地方写。[`handleRefresh`](../../brain/server.js#L990) 收到新信后问模型两句，
写 `next_action` + `next_touch_at`，还在卡里说一句「我看下一步该：…（依据：…）」。
提示词里甚至明写着要判「新信有没有让卡上那条待办**过期**？（比如「没回就催」
而对方回了。）」——你要的那个前提，当初想到了。

**但这条路整条断了：**

- `refreshPursuit` 在 [App.jsx:26](../../src/App.jsx#L26) import 了，
  **全文再没被调用过**（`runRefresh` 跟着 8/06 那一刀走了）
- 全局收信走的是 `/mail/sync` → `incremental()`，**纯收信，不消化**
- 就算它写了，`next_action` 在卡面上也不显示了（8/12 删了 `actionLine()`）

所以你现在看到的「Fairwind 说到时候再 follow up」，是一条**聊天记录里的历史消息**。
翻上去看得见，到了日子什么都不会发生，对方中途回了也没人管。

### 二、同一件事两套实现

「他回你了」在机会线是卡面底行的 `新来信`（一句事实），在人那边是 `repliedCue`
（一条带天数的由头）。两套代码、两种措辞、两个位置。8/12 那份稿子把这一条
记成了病，然后明说这一刀不治。

### 三、由头列表判据只有一条硬规则

`repliedCue` 的全部判据是「往来里最后一封邮件是对方发的」
（[cues.js:82](../../src/lib/cues.js#L82)）。它不看那封信**要不要回**，
也不看**过了多久**。于是：

- 「谢谢，回头见」这种本来就不用回的，永远挂着
- 半年前那封和今早那封，长得一模一样、并排列着
- 它**从不过期**——所有你没回过的信，全堆在那一页上

条目多不是 bug，是判据只有一条的必然结果。

## 二、新规矩：通知条目一条都不存

**全部现算。** 存的只有三样，而每一样都是**关于一个不会变的事实的**记录：

| 存什么 | 锚在哪个不变的事实上 | 存哪 |
|---|---|---|
| 这封信要不要回 | **那一封信的内容**（信寄出去就不会再改） | 库 `letter_verdicts` |
| ✓ 你打的卡（办完了） | **某一条由头的身份**（谁 + 哪种 + 依据哪天） | 库 `cue_marks` |
| ✕ 你说先不看 | 同上 | 库 `cue_marks` |

### 为什么不存条目

你说的最后那句「邮箱里查到我发出了相应信件就自动勾掉」，在现算的世界里
**根本不是一个功能，它是现算这件事本身**。

`bumpCue` 已经是这样了：它不存任何待办，每次现算 `unansweredRun`——
你连着发出去、中间没人回的最后几封。你一回信，这串就断了，那条通知自己就没了。
**没有谁去执行「勾掉」，也就没有「该勾没勾上」这种 bug。**

反过来，`next_action` 那套（存一条待办，收信时让模型判它过期没）就得真去
实现「自动勾掉」，而且**它只在收信时才有机会判**——你从别的信箱回的、
你在会上当面说的，它永远不知道。

`cues.js` 开头那句原话已经把这条规矩写下了：
**「能算出来的就算，算不出来的才存。存下来的东西会跟事实分叉，算出来的不会。」**

### 为什么「这封信要不要回」可以存

因为它跟 `next_action` 不是一回事。`next_action` 是关于**全局现在该干什么**的
判断——新事实一来它就分叉。「这封信要不要回」只关于**那一封信的内容**，
而信的内容永远不变，所以这个判断永远不会过期。

判过就算数，跟 `address_verdicts`（判一次地址、名下历史往来当场归位）
是同一种东西。

## 三、一条通知长什么样

```
┌──────────────────────────────────────────────┐
│ Sarah Chen · Paperbark Books           ✓  ✕ │
│ 8/16 她回你了，问三月能不能来一周            │
│                                    [打开卡片] │
└──────────────────────────────────────────────┘
```

- **第一行**：谁 · 哪条线（人没挂线就只有名字）
- **第二行**：`why` —— 一句**带日期带来源**的人话。这是现有由头的规矩，照搬。
- **`✓`**：办完了。上库，跨设备。
- **`✕`**：先不看。也上库（见第九节，这一条推翻了旧论断）。
- **[打开卡片]**：机会线开那张机会卡，人开那张名片。

**通知条里不写 Fairwind 的建议**，理由见第十节。

## 四、由头合成一套

一条通知 = 一个**由头**，挂在一个**对象**上。对象有两种：`contact` 和 `pursuit`。
判据两边共用同一份代码。

| via | 对人 | 对机会线 | 判据 | 怎么灭 |
|---|---|---|---|---|
| `replied` | ✓ | ✓ **（新）** | 往来里最后一封是对方发的，且这封信判为「要回」，且已过 `not_before` | 你回信 / ✓ 打卡 |
| `bump` | ✓ | ✓ **（新）** | 你连发没回音，按 `BUMP_WAIT = [7, 21]` 到点 | 对方回信 / ✓ |
| `circleback` | ✓ | ✓ **（新）** | `next_touch_at` 到了 **且那之后没有对方来信** | 对方回信 / 到日子后你回信 / ✓ |
| `thanks` | ✓ | — | 有 `intro_by`、对方回过你、还没回谢 | 回谢 / ✓ |
| `met` | ✓ | — | 见面记录后 48 小时内没发出信 | 发信 / ✓ |
| `deadline` | — | ✓ **（新）** | 有 `deadline_at` 且 14 天内或已过 | ✓ |

### 三条要说明的

**`replied` 吃掉机会线的「新来信」。** 卡面底行那句 `{对接人} · 新来信` 保持不变——
它是卡上的事实标记，跟通知不是一个位置。变的是：以前这件事在人那边和机会线那边
各有一套算法，现在只有一套。

**`circleback` 补上了前提。** 现在的 `circlebackCue` 是「到日子就响」，
不管你俩中间聊没聊过。加上「那之后没有对方来信」这一条，它才是你说的
「到那个时间对方没回我才需要 follow up」。这也正是断掉的 `handleRefresh`
本来想用模型事后作废去解决的那件事——现算不需要作废。

**`deadline` 是 8/12 留下的那个容器。** 那份稿子把「紧急」筛选开关留着，
说「往里放什么，等卡面这一刀落地之后再定」。放这条。

### 红点不进通知栏

红点说的是「Fairwind 说了话你没看」——那是**未读**，不是**该动**。
把它塞进通知栏，通知栏就会退化成「有什么没看」，而这一栏承诺的是
「有什么等你动」。红点留在卡上，规矩一个字不改。

## 四·五、判据算在哪：库供事实，JS 拼由头

**这一节是写施工计划时补的，它拦下了一次旧事故的重演。**

`loadPursuits.js` 开头记着那次事故：

> 首页**不再拉消息**。原来为了算小红点，这儿每 8 秒把全库消息拉一遍。
> PostgREST 默认封顶 1000 行——过了这个数它只返回**最老的** 1000 条，
> 新消息静悄悄不在里面而且不报错。

所以「判据两边共用同一份代码」这句话，如果那份代码是浏览器里的 JS，
它就得先把全部往来拉进浏览器——**那个事故会原样重演一次**。
人那边现在能这么干，只是因为「库里十来个人」（`loadContacts.js` 自己写着的），
机会线不行。

### 但也不能把判据搬进 SQL

那样 `cues.js` 和视图就是两套实现——**第二条病换个地方复发**，
而且 SQL 那份没有测试（这个仓库的测试只跑 `node --test`）。

### 分工

| | 谁算 | 为什么 |
|---|---|---|
| **事实** | 库（一个视图，一行一个对象） | 数量级锁死：对象几十个，不是信几千封 |
| **由头** | JS（`cues.js`，一份） | 判据要能测；测试只跑得了 JS |

视图 `v_pa_cue_facts`，一行一个对象（人或机会线），只有标量：

```
subject_kind      'contact' | 'pursuit'
subject_id        uuid
name              显示用
line_title        机会线标题（人挂了线才有；没有就 null）
last_in_at        最后一封对方来信什么时候
last_in_id        那封信的 gmail_message_id  ← 第五节靠它去查判定
last_in_from      谁发的
last_in_subject   信的主题（通知条上摘一句用）
last_out_at       最后一封你发出去的信什么时候
unanswered_n      你连着发出去、中间没人回的最后几封，几封
unanswered_at     那一串里最后一封的日期
next_touch_at     说好什么时候再碰
next_touch_why    那个日子的出处
deadline_at       截止（机会线才有）
intro_by_name     介绍人（人才有）
intro_thanked_at  回谢了没有（人才有）
org_ever_replied  对方回过你没有（thanks 的前提，人才有）
last_meet_at      最后一次见面记录（人才有）
met_followed_up   见面之后发出过信没有（人才有）
checkin_at        「聊过了」打卡到哪天（人才有，沿用 last_touch_src='checkin'）
```

`cues.js` 的入口从 `cuesFor(contact, msgs, opts)` 改成
`cuesFor(facts, opts)`——**它不再需要看见任何一封信**，
只看这一行标量。现有那些判据一条不改地照搬：
`unansweredRun(msgs).length` 变成 `facts.unanswered_n`，
「最后一封是对方的」变成 `facts.last_in_at > facts.last_out_at`，
其余同理。

**测试全部照旧能跑**，而且比现在好写——不用再造一串假邮件，
给一行标量就行。

## 五、治「那封信本身就不用回」——三层漏斗

第一、二层**已经建好了**，这一刀只加第三层。

| 层 | 判什么 | 靠什么 | 成本 | 状态 |
|---|---|---|---|---|
| 1 | 群发、通知、no-reply | `mail_headers.bulk`（信头里就看得出） | 零 | **已有**（0045） |
| 2 | 这个地址是不是真人 | `address_verdicts.verdict` | 一地址一次 | **已有**（0045） |
| 3 | 这封信要不要回 | 模型读内容 | 一封信一次 | **新增** |

前两层挡掉的绝大多数，根本到不了第三层。第三层要判的是真人写给你的、
但**不需要你回**的那些：「谢谢，回头见」「收到了，月底再联系」「祝好，
期待春天见」。

### `letter_verdicts`

```sql
create table producer.letter_verdicts (
  gmail_message_id text primary key
    references producer.mail_headers(gmail_message_id) on delete cascade,
  needs_reply  boolean not null,
  not_before   date,          -- 要回，但不是现在（第六节）
  why          text not null, -- 一句人话，你看得见它凭什么这么判
  judged_at    timestamptz not null default now()
);
```

命名跟 `address_verdicts` 对齐：**同一种东西——判一次、永远算数。**

### 什么时候判：懒算，批量

**不在收信时判。** `incremental()` 现在是纯收信，往里加模型调用会让全局同步
变慢变贵，而且**你不看的信也要付钱**。

改成：**打开通知栏时，把还没判过的来信一次性交给模型判一批。**
一次请求判 N 封，比 N 次请求判 1 封便宜一个数量级。第一次打开慢几秒，
之后全是缓存。

**判哪些信：不是全部历史来信。** 只判**此刻会成为候选的那些**——
每个对象（人 / 机会线）往来里的**最后一封对方来信**，且过了前两层漏斗，
且 `letter_verdicts` 里还没有它。这把一次的量锁在「你有多少个对象」
这个数量级上（几十），而不是「你收过多少封信」（几千）。

对方再回一封新的 → 那是一封新信，重新判一次。旧那封的判定留着不动，
它以后不会再被问到。

跟第十节的 B 是同一条道理：**不看就不花钱。**

### 判不出来的时候

模型没答上、格式不对、网断了——**一律当「要回」。**

宁可多吵你一条，也绝不许因为一次调用失败就把一封真信悄悄咽掉。
这一条跟收信那边「消化失败不吞掉收信成果」是同一个规矩。
失败的不写 `letter_verdicts`，下次打开重判。

### 判错了怎么办

`why` 是要显示的——你在通知栏能看到「判为不用回：他说的是『谢谢，回头见』」。
被判掉的信**不消失**，进「老账」那一层（第八节），有数字、点得开、看得见理由。
判错了你自己能捞回来。

**静默筛掉是这个项目最不能忍的那种谎。**

## 六、治「要回，但不是现在」

同一次判断顺手出 `not_before`。问「这封要不要回」和「什么时候回」是
**同一个问题的两半**，一次模型调用出两样，不多花一分钱。

他信里说「circle back next semester」→ `not_before = 2027-01-15`。
这条通知在那天之前**不出现**；到了那天，还得再过一遍
「那之后有没有对方来信」的前提，才真的响。

日期是**从他的原话里读出来的事实**，不是系统编的——所以它值得存。
这就是前面讨论里定下的「日子存，前提现算」。

`why` 里带上出处：`他说 "circle back next semester" → 1月15日 到了`。
**日期永远说得出出处**，这是 `circlebackCue` 现有的规矩，照搬。

## 七、治「已经处理了，只是没留下痕迹」——✓ 打卡

当面说了、打了电话、从别的信箱回的——系统无从得知。只能你自己按一下 ✓。

```sql
create table producer.cue_marks (
  id           uuid primary key default gen_random_uuid(),
  profile_id   uuid not null references producer.profile(id),
  subject_kind text not null check (subject_kind in ('contact', 'pursuit')),
  subject_id   uuid not null,
  via          text not null,
  fact_at      date not null,     -- 依据那条事实的日期
  mark         text not null check (mark in ('done', 'off')),
  marked_at    timestamptz not null default now(),
  unique (profile_id, subject_kind, subject_id, via, fact_at)
);
```

**键锚在事实的日期上，不是锚在措辞上**——这是 `cueKey` 现成的规矩
（[cues.js:187](../../src/lib/cues.js#L187)），一个字不改地搬过来：

> 「3 天没回」明天变成「4 天没回」，拿 `why` 当键的话你今天关掉的明天又冒出来。
> 拿 `at` 当键就对了：**他再回你一封新的，`at` 就变了，这条由头理应重新出现**
> ——那是新事实，不是你关过的那条。

`profile_id` 恒等于那唯一一行 profile，带上它是为了以后真有第二个人时不用拆表
（`pursuit_seen` 同一个做法）。

现有的 `last_touch_src = 'checkin'` 那条路**留着不动**——人那边的「聊过了」
打卡是名片上的一个动作，跟通知栏的 ✓ 是两个入口。`repliedCue` 里那段
「打过卡而且在这封信之后就不再吵你」的判断照旧生效。

## 八、治「欠了很久的」——分两层，不筛掉

```
  手头（4）
  ├ Sarah 8/16 回你了，问三月能不能来一周
  ├ Paperbark 8/11 发出去，7 天没回音（第 1 次碰）
  ├ LACHSA 他说 "circle back next semester" → 1月15日 到了
  └ Ruth Asawa SOTA 3月1日截止，还有 11 天

  老账（17）                                        ▸
  被判为不用回的（9）                                ▸
```

- **手头** = `fact_at` 在 **7 天**内。7 天不是新发明的数，是
  `BUMP_WAIT[0]`——项目里已有的那个节奏常数。
- **老账** = 7 天以前的。**默认收起，但数字一直露在外面。**
- **被判为不用回的** = 第五节第三层挡下的。同样收起、同样露数字、
  点开看得见每一条的 `why`。

三层**都点得开、都数得出来**。这一条不许打折：

> 关掉多少条都得说出来，而且永远留一条放回来的路。静默藏起来 =
> 你以为没有，其实有。
> —— [People.jsx:167](../../src/components/People.jsx#L167)

## 九、✕ 也上库（推翻 `cueoff.js` 的旧论断）

`cueoff.js` 开头写着：

> 存 localStorage，**不上库**——关掉一条由头不是事实，是「我这台机器上先不看它」。

**论断本身没错，但结论要改。** 8/08 那份稿子里有一次当场证死的事故：

> 两个窗口同时开着同一个 `localhost:5173`，一个主题亮一个暗，
> 顶栏「过卡」一个 `1/2` 一个 `1/1`。**两份存储各记各的，刷新不会收敛。**

`pa_seen` 因此进了库。`pa_cue_off` 是同一个形状的地雷，只是还没踩到——
而通知栏一旦成为**唯一入口**，踩到它的代价比过卡队列大得多：
你在笔记本上处理完的一摊，回到台式机全部重新冒出来。

所以 ✕ 和 ✓ 都进 `cue_marks`，用 `mark` 一列分开。两者语义仍然不同：

- **`done`** = 办完了
- **`off`** = 先不看

分开存是为了**「都放回来」只放回 `off`，不动 `done`**——你按错了 ✕ 能全捞回来，
而不会把真办完的一起翻出来。

`cueoff.js` 整个删掉。旧的 `localStorage['pa_cue_off']` **开机时读一次、
迁进库、再清掉**——已经关掉的那些不许在这次改动里悄悄复活。

## 十、Fairwind 怎么回：点开才生成

通知条里**只有事实**：谁、哪天、说了什么、多少天了。
想听建议，点 **[打开卡片]** 进卡，在那儿跟 Fairwind 聊——那儿本来就能聊，
而且流式吐字（8/14 那一刀建的）。

**为什么不在收信时先把建议写好存起来：** 那句建议会过期。
你后来又收到一封、或者你在别处已经回了，那句建议还挂在那儿，说的是三天前的
情况。**这正是第一条病换个位置复发。**

**为什么通知条自己得把事实说足：** 「Sarah 8/16 回了，问你能不能三月来一周」
——这句话不花钱就有（信的原文在库里，摘一句即可）。你扫的时候看事实，
觉得这条要动了，再点进去听建议。

## 十一、顶栏上的位置

```
  … 通讯录   过卡 · 3      🔔 4
```

- **🔔 的数字 = 「手头」那一层的条数。** 老账和被判掉的不进这个数字——
  它们随时点得开，但不该天天在你眼前报警。
- **跟「过卡 · N」并排，不合并。** 两个数字说的是两件事：
  队列说「这批还剩几张」（一次批量操作的进度），通知说「有几件事等你动」
  （持续欠着的那摊）。[App.jsx:572](../../src/App.jsx#L572) 那段注释
  已经把这个区别写清楚了。

### 人际管理页的「现在该动的」区块删掉

同一件事两个位置**正是第二条病的形状**。通知栏是唯一入口。

人际管理页留着它真正独有的：按人浏览、通讯录、名片。

---

## 十二、这一刀不做的

- **不做应用外的通知**（邮件摘要 / 推送 / 桌面提醒）。这一刀只做「打开 app
  就一眼看得见」。要不要在不开 app 的时候也知道，是另一场讨论。
- **不重做 `next_action`。** 库里那几个字段和 RPC 继续留着不动。
  `handleRefresh` 里的消化环节**也不接回去**——通知栏现算之后，
  它想解决的问题已经没了。（但代码留着，删它是另一场讨论。）
- **不动卡面。** 四个信号一个不改，红点规矩一个字不改。
- **不动过卡队列。**

## 十三、验收

1. **Fairwind 说的 follow-up 真的会响。** 一条线上你发出去 7 天没回音 →
   通知栏出现「N月N日发出去，7 天没回音（第 1 次碰）」，点 [打开卡片] 到那张卡。
2. **对方中途回了，它自己就没了。** 接上条，让对方回一封 → 那条 bump 通知消失，
   **不需要你点任何东西**；同时出现一条 `replied`。
3. **说好的日子到了才响，而且中途聊过就不响。** 一条线 `next_touch_at` 设成昨天：
   - 那之后没有对方来信 → 通知栏有 `circleback`，`why` 里带得出日期的出处
   - 那之后有对方来信 → **不出现**（现在的 `circlebackCue` 这一格是会出现的）
4. **「谢谢，回头见」不吵你。** 收一封这样的信 → 不进「手头」，
   进「被判为不用回的（N）」，点开看得见 `why`。
5. **判错了捞得回来。** 接上条，把那一层展开，每条都在，一条都没丢。
6. **✓ 跨设备。** A 窗口按 ✓ → B 窗口刷新，那条也没了。
7. **✕ 跨设备，而且都放回来只放回 ✕ 的。** A 窗口 ✕ 掉两条、✓ 掉一条 →
   B 窗口刷新，三条都不在；按「都放回来」→ ✕ 的两条回来，✓ 的那条不回来。
8. **旧的关掉记录不复活。** 升级前在 `localStorage` 里关掉的那些，
   升级后依然是关着的。
9. **老账数得出来。** 7 天以前的欠账全在「老账（N）」里，N 是真数，展开一条不少。
10. **🔔 的数字 = 手头那层的条数**，跟展开后数出来的一致。
11. **通知栏第一次打开会判一批新信**（慢几秒，有转圈），第二次打开秒开。
12. **人际管理页上再也没有「现在该动的」那个区块**，通讯录和按人浏览照旧。
