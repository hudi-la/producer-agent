# 人际管理：把「人」立成独立一层

2026-08-08

## 零、这一刀要解决的那件事

邮箱里躺着一封信。发信的人叫 Maisa，是 Tom Leeser 介绍的。你联系了他，他回了，现在该你回他。

**你打不开这封信，因为一打开就得写。** 上下文你都记得，该不该回你也判断得了——卡住的只有一件事：**下不去笔**。

而系统帮不上忙，因为 Maisa 不是一条机会线。库里所有起草的机器（认领 thread、拉信、写草稿、放进 Gmail 草稿箱）第一列都是 `pursuit_id not null`。他一步都上不去。

这一刀就是让这套已经造好的机器，**能跑在没有机会线的往来上**。

## 一、推翻了什么

[2026-08-04 board 设计稿](2026-08-04-board-and-layout-design.md)里说：人际管理装的是「没有 proposal 压力的朋友」，和项目争取是两批不同的人。

**这句是错的。** 真实需求里举的例子没有一个符合它：

- **Kirk / Sarah / Mattie** —— 恰恰是挂在机会线上的外联对象，却要在人际管理里有名片
- **老邮箱那份通讯录** —— 朋友和机构的人混在一起，不打算分，要的是「有新作品能一次发给他们」
- **Maisa** —— 既不是朋友（有事要办），也还没形成任何机会线

真正的分法是：

> **人是一个独立的层。项目争取和人际管理是看这一层的两个入口，共用同一张名片。**
>
> 区别在**谁在推你**：有交付压力的，机会线推；没有的，由头推。人本身是同一个人。

那张对照表比的是「两种驱动力」，不是「两种人」。

### 顺带纠正的两条

- **「一条线只能挂一个联系人，套磁装不下」** —— 不成立。[一叠](../../src/components/Pipeline.jsx)按 `task_id` 折：套磁是一条造卡任务造 8 张卡（一人一张）折成一叠。**套磁和媒体外联今天就能跑**——一叠（一批人）+ 说一句…（勾一批、说同一句、各答各的）正好是那个形状，不需要新东西。
- **套磁 / 联系媒体归哪个区** —— 归**项目争取**。判据没变：有没有要交出去的东西。

## 二、美国 networking 的几条，以及它们怎么改了设计

这些不是背景知识，是直接改了引擎形状的判据。

**① 渠道是分层的，层级本身携带信息**

| 渠道 | 意味着什么 |
|---|---|
| Email | 唯一的正式渠道。机构、策展人、教授、画廊、经纪、媒体，第一次联系一律邮件。**冷发邮件完全正常，不算冒犯**（跟中文圈很不一样） |
| 短信 / iMessage | 已经熟了才用。**从邮件转到短信是明确的关系升级信号** |
| Instagram DM | 当代艺术圈的真渠道，比 LinkedIn 重要得多 |
| LinkedIn | 学术 / 商业圈强，艺术圈弱 |
| WhatsApp | 主要是国际联系人（欧洲 / 拉美 / 中东），美国本土人少用 |

→ 用户「微信那拨人和邮件那拨人几乎不重叠」**不是巧合**，是关系阶段和圈层的自然结果。

**② Warm intro 有个大多数人不做的闭环**

规范动作两步：回信时把介绍人挪到 BCC 并明说（不再打扰他）；**过阵子单独回介绍人一句「跟他聊了，谢谢」**。第二步大多数人不做，做了的人会一直有人愿意介绍。

→ 变成由头③，以及名片上的 `intro_by` / `intro_thanked_at`。

**③ Follow-up 的节奏有公认规矩**

发出去没回音：约一周后 bump（一两句，别重发原文）→ 再等两三周 → 第三次还不回就停。**不回 ≠ 拒绝**，多数是淹了。三次不算烦人。

→ 变成由头①和它的三次上限。

**④「circle back next semester」是真话，不是客套**

[0011 迁移](../../supabase/migrations/0011_outreach.sql)开头记的 LACHSA「circle back next semester」、Ruth Asawa SOTA「there is interest」，在美国语境里**是真的邀请你在那个时间点再来**。

婉拒长的是另一个样子：「not a fit at this time」/「we don't have capacity」，而且**不给时间锚点**。

→ 判据很干净：**给了时间锚点的是真的，没给的是婉拒。** 变成由头②。

**⑤ 纯问候在美国是低效的，甚至有点讨嫌**

「Just checking in」/「hope you're well」是公认最没用的邮件类型。有效的 keep-in-touch **一定带由头**：我有新作品了 / 我看到个东西想到你 / 我下个月要去你的城市 / 恭喜你那个展。

→ **这条推翻了「定时打招呼」这个功能的形状。** 引擎不该产出「该问候了」——那句话没法写。它该产出**「该给他看点什么了」**。

**⑥ 见面之后那 48 小时**

Opening、artist talk、conference 是美国 networking 的主场。见完 48 小时内一封 follow-up。不发这封信，那次见面基本等于没发生。

→ 变成由头④，由「记一笔」触发。

**⑦ 群发是标准做法，不算打扰**

艺术家给整份名单发 newsletter（新作品、开幕、年度回顾）完全正常。年底、新作发布、开幕、搬城市是天然节点。

→ 「导通讯录 + 有新作品快速群发」完全对路。**但不在这一刀里**（见第七节缓办）。

### 由此得到的核心判断

> **「多久没碰」不是引擎，「由头」才是。** 冷却时间只是排序用的——它决定先找谁，但它不足以让你动笔。

而且前三种由头**恰好全落在邮件那拨人身上**，也就是最需要帮忙的那拨。微信那拨人在这一刀里就是通讯录 + 名片，**不装引擎，也不假装知道你们多久没聊**。

线下见面用户愿意手动记一笔，所以那块有解（由头④）。

## 三、人这一层的结构

### contacts 从「外联的附属」变成第一公民

现有五个字段（`name / email / org / role / notes`）不动，加六个：

| 字段 | 干什么用 |
|---|---|
| `channels jsonb` | `[{kind, value, primary}]`，kind ∈ `email\|wechat\|sms\|whatsapp\|ig\|phone` |
| `intro_by uuid` → contacts | 谁介绍的 |
| `intro_thanked_at date` | 回谢了没有 |
| `last_touch_at date` | 上次碰是哪天 |
| `last_touch_src text` | **这个日期从哪来的**：`email` / `checkin` / `meet` |
| `cadence_days int` | 你给这个人定的节奏，null = 不管 |
| `next_touch_at date` | 什么时候再碰他（由头②写这里，你也能手填） |
| `next_touch_why text` | **这个日期哪来的**，存原话：`他说 "circle back next semester"` |

`next_touch_at` 这个名字是照抄 `pursuits.next_touch_at`（0011）的——同一个意思，同一个引擎，不该有两个名字。

**为什么放在人身上而不是 thread 上**：一个人同一时间基本只有一个「什么时候再碰」。放 thread 上会出现同一个人两个日期，那就得再决定听谁的——凭空多一个判断。

两个刻意的决定：

- **`email` 那列不动。** 它上面的唯一索引（0011）是去重的地基。`channels` 是补充不是替代——为了整洁把地基拆了不值得。
- **`last_touch_src` 不是装饰。** 卡上永远得说得出「上次 3/12，来自那封邮件」还是「上次 5/2，你自己记的一笔」。这是 `「到日子了」也得说得出是哪个日子` 的直接落实。没有这一列，冷却时间就是个来路不明的数字。

**关系强度分层不存** —— 算出来的。存了迟早跟事实分叉。

### 往来改挂人：三张表，一个约束

`pursuit_messages`、`pursuit_threads`、`deliverables` 三张表现在第一列都是 `pursuit_id not null`。全部改成：

```sql
pursuit_id  uuid  null          -- 改成可空
contact_id  uuid  null          -- 新增，references producer.contacts(id)
check (pursuit_id is not null or contact_id is not null)
```

**要么挂线、要么挂人，至少有一个。** 两个都空 = 无主数据，数据库层面就不允许。

`pursuit_threads` 的主键现在是 `(pursuit_id, gmail_thread_id)`，换成代理主键 + 两条唯一索引（按线一条、按人一条）。

**表名不改。** `pursuit_messages` 装的已经不只是机会线的消息了，名字确实不准。但改名要动 brain 里一串 RPC、两个视图、前端一堆引用——**纯代价、零收益**。加 `comment on table` 说清楚就够。

### 两种消息怎么分：靠已有的东西，不加新标记

| | 判据 | 归谁 |
|---|---|---|
| 跟外面的人的真实往来 | 有 `gmail_message_id`，role 只能 `org\|artist`（[0027 有硬校验](../../supabase/migrations/0027_deliverables_and_threads.sql)） | **人** |
| 你跟 Fairwind 的商量 | 没有 gmail id，role 是 `producer\|artist` | **线** |

这个界线不是发明的，是数据自己已经分开了的。

### 迁移：一封都不能没有主

1. 有 `gmail_message_id` 的消息 → 从它所在 pursuit 的 `contact_id` 取人，写进 `contact_id`
2. **那条 pursuit 没有 contact_id 的** → 从邮件的 `from`/`to` 认人：库里有这个邮箱就挂上去，没有就建一个新联系人
3. `pursuit_threads` 和 `deliverables` 照 pursuit 的 contact 补一份引用

第 2 步会**自动建出几个新联系人**。这不是副作用——这正是 Kirk / Sarah / Mattie 之外那些人第一次进系统。迁移跑完后人际管理页上会出现没手动加过的人，这是对的。

**验收（跑得出来，不等就回滚）：**

```sql
-- 迁移前
select count(*) from producer.pursuit_messages where gmail_message_id is not null;   -- = N
-- 迁移后，必须还是 N
select count(*) from producer.pursuit_messages
 where gmail_message_id is not null and contact_id is not null;                       -- 必须 = N
```

## 四、四种由头

原则：**能算出来的就算，算不出来的才存。** 存下来的会跟事实分叉，算出来的不会。

| 由头 | 怎么来的 | 新存字段 |
|---|---|---|
| ① 该 bump 了 | **算**：thread 最后一封是你发的，且过了该轮的等待期，且还没碰满三次 | 不要 |
| ② 到日子了 | **存**：brain 收信时认出时间锚点 → `next_touch_at` ≤ 今天 | 用第三节那两列 |
| ③ 介绍人还没回谢 | **算**：`intro_by` 非空 + **被介绍人回过你至少一封** + `intro_thanked_at` 为空 | 不要 |
| ④ 见面 48 小时信 | **你记的那一笔**触发 | 不要 |

三处判据说细一点，免得实施时各写各的：

- **①「该轮的等待期」不是固定 7 天**，照第二节③那条节奏走：第 1 次碰等 7 天，第 2 次等 21 天，然后停。等待期从 thread 里**最后一封你发的信**算起。
- **③「有过往来」= 对方回过你至少一封**（该 contact 名下有 `role='org'` 的消息）。只发出去没人回，谈不上「聊完了」，这时候去回谢介绍人是尴尬的。
- **④ 的 48 小时不是延迟，是过期提示。** 记一笔当场就问「要不要现在起草那封信」；你没起草它就进队列，超过 48 小时**仍然不消失**，只是卡头改口——「8/6 见的，已经过 48 小时了」。消失等于替你决定放弃。

### ④ 记一笔：不用新表

`pursuit_messages.role` 早就有 `note` 这个值（[0003](../../supabase/migrations/0003_pursuits.sql) 就定了，一直没人用）。线下见面记一笔就是它：

```
role='note', kind='meet', contact_id=<那个人>, content='8/6 CalArts 开幕，聊了他在做的声音项目'
```

一条记录同时干三件事：更新 `last_touch_at` / `last_touch_src='meet'`、触发由头④、留下「上次聊到哪」的内容。**不是三个功能，是同一笔。**

### ① 的三次规矩：停了要明说

「碰过几次」从数据算得出来：一条 thread 里**连续的、你发的、中间没有对方回复的**邮件数。到三次就不再产生由头。

但**卡上不能就这么消失**，要留一句「已经碰过三次，停了」。消失 = 你以为系统还在管，其实早放弃了。这是 `红点不再撒谎` 的同一件事。

### ② 认不出来就闭嘴

brain 收信时顺带认时间锚点（*next semester* / *after March* / *in the fall*）：

- 认出来 → 写 `next_touch_at`，同时把**原话**写进 `next_touch_why`，卡上标明「他说 "circle back next semester" → 我算成 9/1」
- **认不出来 → 什么都不写**，不猜、不用默认值

名片上永远留一个手填日期的口。所以它认得准是加分，认不准也不会拖住这一刀，更不会瞎猜。

**这是整刀里唯一一个「调出来的、没有明确完成时刻」的东西**，所以它必须能干净降级。

### 接进过卡队列

[queue.js](../../src/lib/queue.js) 那条注释预言了这一天——*「via = 什么送它进来的。第一刀只有 'pick'…字段先留着，免得那时候还要迁存储。」*

**改一：队列项要能装人**

```js
// 旧：{id, via, skipped}         id 是 pursuit_id
// 新：{kind: 'pursuit'|'contact', id, via, skipped}
```

`normalize()` 读到没有 `kind` 的老项，一律当 `'pursuit'`——这正是那个函数存在的理由。**localStorage 里现有的队列一项都不会丢。**

去重的键也得跟着从 `id` 换成 `kind + id`，否则两种东西撞 id 时会静悄悄吞掉一项（uuid 撞不上，但这是判据该说对的事）。同理 `at`（你正看着那张）要存 `{kind, id}` 而不是裸 id。

**改二：`via` 加四个值** —— `bump` / `circleback` / `thanks` / `met`

**改三：卡头必须说得出为什么**（`「你为什么在队里」钉进卡头` 定的规矩），每句带日期和来源：

| via | 卡头说什么 |
|---|---|
| `bump` | 3/12 发出去，12 天没回音（第 1 次碰） |
| `circleback` | 他说 next semester 再聊 → 9/1 到了 |
| `thanks` | 跟 Maisa 聊完了，还没回谢 Tom Leeser |
| `met` | 8/6 在 CalArts 见过，48 小时信还没发 |

### 什么时候算：不加定时任务

- ①③ 是纯计算 → 前端加载时算，跟 `needsMe` 一个姿势
- ② 跟着 `/refresh` 走 → 你按「更新最新信息」时顺带认
- ④ 你记一笔当场触发

**一个 cron 都不需要**，跟「按钮取信」的姿势一致。

## 五、页面

### 列表页：先不做分层

四层分层（有来有往 / 久没动 / 从没回过 / 办完事的）**这一刀不做**——它的全部价值在人多的时候，现在库里十来个人，分层只是负担。排序按 `last_touch_at`。判据记在第七节，跟导入那一刀一起做。

页面三样：工具条 + 名片列表 + 点开进详情。工具条两个口子：

- **「加个人」** —— Maisa 进系统的入口
- **过卡入口** —— 跟项目争取那边同一个组件

**队列是一条，不是两条。** 顶栏那个数字说的是「你还欠着几件事」，它是**手头这摊活**，不是某个区的活。两边工具条各放一个同样的入口，显示同一个数字；过卡时卡是机会线就显示机会线，是人就显示人。

### 名片：复用详情页那三栏

不新造形状。[PursuitFocus](../../src/components/PursuitFocus.jsx) 的三栏正好对得上：

| 栏 | 机会线上是什么 | 名片上是什么 |
|---|---|---|
| 左 · 卷宗 | 这条线的来龙去脉 | **谁** —— 名字、机构、角色、channels、谁介绍的、上次碰是哪天**及来源**、你定的节奏 |
| 中 · 商量 | 你跟 Fairwind 商量 | **往来** —— 他名下所有邮件 + 你记的笔 + **他挂在哪几条机会线上** |
| 右 · 交付 | 要交出去的东西 | **要发的信** —— 草稿在这儿，定稿 → 进 Gmail 草稿箱 |

中栏那句「**他挂在哪几条机会线上**」是重点——这是「人是独立一层、两区共用」落地之后**看得见**的样子。Kirk 挂着三条线，名片上一眼就是三条，点得过去。

## 六、验收：Maisa 走通全程

| | 步骤 | 现成的吗 |
|---|---|---|
| 1 | 人际管理 →「加个人」→ Maisa、邮箱、Tom Leeser 介绍的 | 新（简单表单） |
| 2 | 名片上「认领这条邮件往来」→ 登记进 `pursuit_threads` | **新的口子** |
| 3 | 按「更新最新信息」→ `/refresh` 拉回那条 thread | 现成，接受 contact_id |
| 4 | 中栏看得见他回的那封信 | 现成 |
| 5 | 右栏「起草回信」→ brain 写一版 → `deliverable kind='email'` | 现成 |
| 6 | 你改两句 → 定稿（`pa_set_final`） | 现成 |
| 7 | 「放进 Gmail 草稿箱」→ `/gmail-draft` → 你在 Gmail 里按发送 | 现成 |

**七步里六步是现成的**，只是今天都要求 `pursuit_id`。这就是第三节那个结构手术值得先做的原因——做完它，这条流水线自己就通了。

第 6 步之后由头③会自己冒出来：**「跟 Maisa 聊完了，还没回谢 Tom Leeser」**。闭环自动合上。

另外两条验收：

- **迁移前后消息数相等**（第三节那两句 SQL）
- **localStorage 里的老队列读得回来**，一项不少

## 七、明确不做的 / 缓办

> 记在这儿，免得这些取舍只活在一次对话里。

### 缓办一：实时收发信 —— 横在两个版面前面的同一件事

「怎么把邮件实时收进来、发出去」在项目争取和人际管理**两边都没做**。它不是人际管理的一部分，是它俩共同的底座。

这一刀**保留现在的姿势**：按钮取信（`/refresh`）、手动发信（进 Gmail 草稿箱，你自己按发送）。实时那件事单独开一轮讨论。

注意 `create_draft` 而非发送，**不是我们关掉的，是 claude.ai 的 Gmail 连接器整套工具里根本没有 send**（[brain/server.js](../../brain/server.js) 里写明了）。

### 缓办二：扫老邮箱导通讯录

用户的邮箱不超过四年，判据已经定好了，只是不在这一刀里：

- **扫全部历史**
- **判据是「你发过就算」** —— 只要你主动写过信给他。天然滤掉 Substack / Uber / 客服工单那类纯 inbound 噪音，也抓得住 2026-02 那批发了没回的外联
- **直接入库，不用过目**，入库后再筛

**一个已知的可行性风险：** brain 现在 `maxTurns: 20`，四年邮箱分页扫下来肯定不止 20 轮；让 Fairwind 逐封读正文，token 和时间都失控。出路是**这一趟只「数」信不「读」信**——四个判据（回没回 / 回合数 / 最近日期 / 谁先开口）全都只要 thread 元数据。**能不能只拿元数据、一次拿多少，必须对着 `search_threads` 的真实返回验一次**，现在不敢打包票。

还有一条要写明的：[0027](../../supabase/migrations/0027_deliverables_and_threads.sql) 立过一条原则「同步只拉登记过的 thread，**永远不遍历信箱**」。扫老邮箱正是遍历信箱——**这不冲突**：那条原则管的是常驻同步（每次扫全箱，越用越慢越吵），扫老邮箱是一次性手动跑一轮，形状跟 `agency_scout` 那种手动任务一样。区别得写清楚，否则下一个人会以为原则被推翻了。

### 缓办三：筛法 —— 不做「筛」，做「排序 + 分层」

**筛是删，删了就看不见了**，跟「绝不丢信息」直接冲突。而且判据会变：今天没用的人明年可能正好需要。

全部入库，一个不删。默认按关系强度分层，弱的自然沉底——跟 [Pipeline 那个一叠](../../src/components/Pipeline.jsx)同一个形状：折起来，只递一件事「这儿还有 400 个只发过没回过的」，想看展开。

四层，**每层都说得出理由**，不是玄学分数：

| 层 | 判据 | 长什么样 |
|---|---|---|
| 有来有往 | 对方回过你，最近几个月有动静 | 正常名片，排最上面 |
| 回过，但久没动了 | 对方回过，但一年没往来 | 正常名片，标「上次 3/12」 |
| 发过，从没回过 | 你发了，一次没回 | 折成一叠，灰的 |
| 办完事的 | 单条 thread、≤2 封、一年以上没动 | 折成另一叠，更灰 |

判据全部从邮件本身算得出来，一个都不用手标。

**外加一条更值钱的：「谁先开口」要单独标出来。** 那条 thread 的第一封是谁发的，库里算得出来。**别人主动写信给你的人，是比你主动联系的人重得多的资产**——想「我有新作品该给谁看」的时候，这拨人是第一优先。

（不做删除还有个实际好处：群发时你会想知道「这是我第 4 次单方面发给他了」。人删了这句就说不出来。）

### 缓办四：群发新作品

依赖缓办二的产物形状（名单怎么分组、按标签还是手挑）。跟导入一起做。

现有的 [SayTo](../../src/components/SayTo.jsx)（勾一批、说同一句、各答各的）就是它的雏形，形状已经对了。

### 缓办五：收紧 anon

`v_pa_contacts` 现在对 anon 是 revoke 的（0011，因为 notes 里有私人内容），而前端走的正是 anon。**这一刀要把它开给 anon**，否则名片页读不出来。

理由是 [0027 已经写明的既有姿势](../../supabase/migrations/0027_deliverables_and_threads.sql)：*「整个 app 走 anon，没有登录。所以这些视图里的私人内容（邮件正文、关系记忆）anon 都读得到——这是 app 今天既有的姿势…要收紧是另一刀。」*

邮件正文早就对 anon 开着了。**开 contacts 不是新增暴露，是补上一个不一致。** 但不该悄悄发生——记在这儿，跟「收紧登录是另一刀」一起。

### 明确不做

- **一条线挂多个联系人** —— 不需要。一叠已经解决了套磁和媒体外联的形状。
- **改表名** —— `pursuit_messages` 名字不准，但改名纯代价零收益，加注释即可。
- **定时任务 / cron** —— 四种由头都能挂在你已有的动作上。
