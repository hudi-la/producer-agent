# 判据推倒重来：卡上只剩四样

> 上游：[2026-08-10 全局邮件同步](2026-08-10-global-mail-sync-design.md)
> 范围：**只管机会线的卡片。人那边这一刀不碰**，后面单独谈。

## 一、为什么推倒

数了一遍，机会线这边有九条判据，散在四个地方算：

| 判据 | 在哪算 |
|---|---|
| 球权（待处理/等回复） | 库 `v_pa_pursuits.ball_eff` |
| 该干什么（三档优先级） | 前端 `nextAction.js` |
| 截止急不急（14 天门槛） | 前端 `nextAction.js` |
| 小红点 | 库 `v_pa_pursuits.unread` |
| 过卡队列进队 | 前端 `App.jsx` |
| 五种由头（人那边） | 前端 `cues.js` |

它不是设计出来的，是长出来的。三个具体的病：

**一、系统跟你抢方向盘。** 球权有一套「你手动定的能撑到下一件真事发生
（新的对外通信、跟进日到期），之后 Fairwind 重新接管」的规则。也就是说
**你的判断会被系统悄悄改回去**，而你不会收到任何通知。

**二、同一件事有两套实现。** 「他回你了」在机会线是球权自动翻成「待处理」，
在人那边是五种由头里的第一条。两套代码、两种措辞、两个位置。

**三、有一行是死的。** 「该干什么」第一优先级是 `next_action`，而写它的消化
环节（读新信 → 作废过期待办 → 提新的下一步）随 `runRefresh` 一起删掉了。
留着就是一行永远不会更新的字。

## 二、新规矩：系统只报事实，判断归你

卡上只剩四样。**分工是硬的**：

| | 谁说的 | 什么时候变 |
|---|---|---|
| **待处理 / 等回复** | **你点的** | 只有你再点一下 |
| **新来信** | 系统（事实） | 你点开这张卡就灭 |
| **红点** | 系统（事实） | 你点开这张卡就灭 |
| **开始 / 截止日期** | 事实 | 日期本身变才变 |

后三样系统说了算，因为它们是**能查证的事实**——有没有信、看没看过、日期是几号。
第一样只有你说了算，因为「这件事该不该我动」是判断，而判断是你的活。

**系统再也不改你点的标签。** 你点了「等回复」，它就是等回复，直到你自己改。

## 三、卡面长什么样

```
                                          ●     ← 红点：Fairwind 说了话你没看
  ● 待处理                                       ← 你点的标签（可以一个都不点）
  Paperbark Books 工作坊
  ★★★
  截止 spring 2027                               ← 有就显示
  Handmade Paperbark Books

  ● Sarah · 新来信                               ← 有未读外部来信；没有就写阶段
```

底行的规则：

- **有未读外部来信** → `{对接人} · 新来信`
- **没有** → `{对接人} · {阶段}`（沟通中 / 已交 / 谈成 ✓ …）

「新来信」占的是阶段那个位置，不另开一行。**卡面上的位置很贵**，而当这条线
有信在等你的时候，「新来信」比「沟通中」要紧。

## 四、「新来信」怎么算

```
这条线上有 direction = 'in' 的邮件，且 created_at > 你上次看这张卡的时间
```

- 「这条线上的邮件」= `v_pa_pursuit_mail` 里 `on_this_line` 的那些（0052/0053 建的推导）
- 「你上次看这张卡」= `pursuit_seen.seen_at`，跟红点同一个机制
- 点开卡 → `pa_mark_seen` → 两个信号一起灭

**为什么是「看过就灭」而不是「回了才灭」**：卡面只该说一句最要紧的话。
「你还没回这封信」是判断，而判断归你——你觉得该回，就自己点亮「待处理」。
系统的活到「告诉你有信」为止。

## 五、删掉的

- **`ball_auto` / `ball_eff` / `manual_holds`** —— 球权不再自动推算。
  `ballOf(p)` 直接返回 `p.ball`。
- **`actionLine()` 整个**，连同它三档里的每一档：
  - `next_action`（Fairwind 提的下一步）—— 已经没人写了
  - `该碰一下了`（`next_touch_at` 到期）
  - `N 天起开放` —— **但开放日期本身保留显示**，它是事实，只是不再包装成
    「该干什么」
- **`voidedAction` / `doneAction` 在卡上的显示** —— 它们是 `next_action` 的
  附属物

`next_action` 那几个字段和 RPC **留在库里不动**。以后要不要重做「Fairwind 提
下一步」是另一场讨论，现在只是不显示。删列会让那场讨论失去材料。

## 六、两个筛选开关

- **「待处理」** —— 改成筛「**你点了待处理标签的**」。筛的是你自己的判断，
  比原来筛系统的推算实在。
- **「紧急」** —— **留着，判据暂时不动**（有截止日期且 14 天内或已过）。
  它是下一场讨论的容器：往里放什么，等卡面这一刀落地之后再定。

## 七、这一刀不做的

- **人那边一个字不改。** 五种由头照旧。两边判据要不要合，后面单独谈。
- **过卡队列不动。** 你说过卡应该只由批量操作产生——现在它事实上已经是了
  （`runRefresh` 删掉之后，只剩「你勾选过一遍」和「群发之后」两条路）。
  这一刀不需要再动它。
- **不删 `next_action` 的库字段。**

## 八、验收

1. 卡上再也看不到「该碰一下了」「该干什么」那一行
2. 点亮「待处理」，刷新页面、等一轮邮件循环，它**还在**（系统不再改它）
3. 已亮的标签再点一下 → 灭掉，两个都不亮
4. 有未读外部来信的线，底行写「新来信」；点开卡再回来 → 变回阶段
5. 红点行为不变
6. 有开始/截止日期的卡照常显示日期
7. 「待处理」开关筛的是你点亮的那些
